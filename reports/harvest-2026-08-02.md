### 🟢 Strong：`systemd-user-agent`（Linux / WSL 排程 agent）

- **Purpose**：在 Linux / WSL 上建立、除錯、管理 user-level systemd service + timer（agent fleet 的排程）。涵蓋 unit 生成、`systemctl --user` 生命週期、`loginctl enable-linger` 開機存活、timer 語意陷阱、watchdog 重啟、log 位置。
- **Trigger**：
  - 「排程」「定時執行」「開機自動跑」而平台是 Linux / WSL
  - `systemctl --user`、`.service` / `.timer`、`loginctl`、linger
  - 「agent 沒有在跑」「重開機之後就不見了」
  - 從 macOS 搬過來的 launchd 專案要落地
- **Category**：`workflow/`
- **Rationale**：
  - **既有 `launchd-agent` 明文排除這塊**：它的 frontmatter 寫著 `SKIP: Linux (cron/systemd)`，但目前沒有任何 skill 接手，等於留了一個洞。而 rivendell 主線已經整個搬到 WSL。
  - 已經累積了具體、非直覺、踩過的知識，全部有 commit 或程式碼為證：
    - `bf44ff7` — interval timer 要用 `OnActiveSec` 而非 `OnUnitActiveSec`，否則載入當下就先開一槍
    - `b27a54d` — watchdog 從 `launchctl` 移植過來才抓得到 hung service
    - `bin/lib/platform.sh:48` — WSL 的 systemd 是 opt-in（`/etc/wsl.conf` 的 `[boot] systemd=true`），沒開的話 pid 1 是 init，每個 `systemctl` 都吐難解的錯 → 必須先驗 `ps -p 1 -o comm=`
    - `svc_boot_persist` — WSL 沒有 boot-time login，linger 才是關鍵（macOS 上是 no-op）
    - session 21 在 prod 上實際用的探測三連：`is-enabled` / `is-active` / `loginctl show`
  - `bin/lib/platform.sh` 的 `svc_*` 介面已經是現成的 skill 骨架（"When adding a third platform, this file is the whole diff"）— skill 可以直接把這個 adapter 模式當作 reference implementation。
- **建議結構**：
  - `SKILL.md`：平台偵測 → unit 生成 → 載入 → 驗證 三段流程
  - `references/timer-semantics.md`：`OnActiveSec` vs `OnUnitActiveSec` vs `OnCalendar`、`Persistent=true` 的補跑行為
  - `references/wsl-gotchas.md`：`[boot] systemd=true`、linger、無 GUI session、`XDG_RUNTIME_DIR`
  - `templates/`：oneshot+timer、keepalive service、watchdog
  - `references/launchd-mapping.md`：launchd ↔ systemd 對照表（給搬遷用）

### 🟢 Strong：`portability-sweep`（主機專屬寫死掃描）

- **Purpose**：靜態掃一個 repo，找出綁死在特定主機/OS/使用者的東西，改成可攜形式。包含：絕對家目錄路徑（`/Users/xxx`、`/home/xxx`）、寫死的 runtime 版本路徑（`.../node-v20.11.0/bin/node`）、BSD-only 語法（`sed -i ''`）、macOS-only 執行檔（`launchctl`、`pbcopy`、`open`）、寫死的 repo/專案名。輸出：問題清單 ＋ 每項的可攜替代寫法。
- **Trigger**：
  - 「改成不寫死的路徑」「這台跑得動另一台跑不動」
  - 要把專案搬到另一台機器 / 另一個 OS / 交給別人
  - `sed: -i may not be used with stdin`、`launchctl: command not found` 這類錯
  - 新增 `bin/` 腳本或 docker-compose 之前的 pre-flight
- **Category**：`quality/`
- **Rationale**：
  - **n≥4 且橫跨專案**：session 23（pti-ares node 路徑寫死）、session 24（`docker-compose.yml` 寫死 `/Users/manibari/code`，見 `deployment-inventory.md`）、commit `38a07d2`（BSD `sed -i ''` → GNU）、commit `b27a54d`（launchctl）。專案 CLAUDE.md 甚至已經有一條手寫規則「Never hardcode the repo/project name — 從 `basename "$PWD"` 推導」。**規則已存在但沒有執行機制**，這正是 skill 該補的位置。
  - 既有 skill 不覆蓋：
    - `env-doctor` 是 **runtime 探測**（跑起來檢查版本/依賴/連線），這支是 **原始碼靜態掃描**，發生在搬遷之前而不是之後。兩者互補，可以串：sweep → doctor。
    - `github-repo-audit` 看的是結構/文件/CI 健康度，不看主機耦合。
    - `protect-secrets` 只掃密鑰。
  - 每一類都有明確、可自動化的偵測 pattern（grep-able），適合做成 `scripts/sweep.sh` + 分級輸出（blocker / warn / info）。
- **建議結構**：
  - `scripts/sweep.sh`：分類 grep + 分級輸出
  - `references/portable-forms.md`：每個反模式對應的可攜寫法（`sed` 的 GNU/BSD 雙相容寫法、`command -v` 取代硬路徑、`$(basename "$PWD")` 取代專案名、docker-compose 的相對路徑 + `${PWD}`）
  - 與 `env-doctor`、`systemd-user-agent` 交叉連結
