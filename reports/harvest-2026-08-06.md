## 二、Skill 候選

### 🟡 Moderate — `repo-contract-brief`（sibling repo 契約優先 + 用直接查證取代假設）

- **目的**：當一個功能被拆到多個 sibling git repo（如本輪 PTI-ARES 拆成 Transcribe=寫入／Translate=讀取渲染／Main=顯示），在開始寫程式前，先（1）用直接查證（`psql`/`docker exec`/`grep`/重新解析原始檔）確認上游真實現狀，而非相信需求描述或既有文件；（2）以消費者視角先寫 `api-contract.md`（誰先寫、需要什麼能力、各用途的資料形狀、endpoint 草案、mock 層、待對齊項），再進 `requirement.md`/`schema.md`。
- **觸發**：「這個功能要接上 [另一個 repo] 的輸出」「我們要拆成多個 repo，要先講好介面」「上游 repo 還沒做完，我要怎麼往下推」。
- **類別**：planning（與 `task-brief`、`requirement` 銜接，介於兩者之間補「跨 repo 契約」這一步）
- **理由**：本輪 3 個獨立 session（#2 Converter/Transcribe、#3 Main、#5 Translate）各自針對同一功能的不同角落，都自發走了「先查真相 → 再寫契約 → 才進 requirement」的順序：
  - #2 在同意「重做」前，先用 `docker exec psql` 查出舊實作已存在、且結構上就是「只存指標、真幾何在外部檔」——這個查證結果改變了重做的正當性判斷。
  - #3 明確把 `docs/api-contract.md` 定調成「Main 消費 Translate」的契約，先於 requirement 存在。
  - #5 在動手前用 `psql` 驗證舊 DB 幾何缺失、並重新解析 PB0009 量化規模，才敢寫自己的 brief。
  - 三次都不是巧合的個人習慣，而是同一個「PG 必須自足、不依賴外部檔」的架構決策（在 #2 記錄於 `memory/pti-ares-repo-split.md`）逼出來的必要步驟。
- **為何只到 Moderate、不到 Strong**：三次發生集中在**同一天、同一個 fleet、同一個功能**（ODB++→PG→渲染管線）由使用者主動拆解出來，比較像「一個計畫被分派到 3 個 repo 各跑一次同款開場」，而非 3 個不相關情境各自獨立重新發現同一模式（對比 `[[skill-apply]]`＝ChimesFlow + PTI-ARES 兩個不相關案子分別發生）。工作流程本身確實可重用，但目前證據只驗證了「PTI-ARES 這個 fleet 內部拆 repo」這一種場景，尚未見到**另一個 fleet 產品**做同款拆分。
- **建議動作**：先不建 skill，記錄進 `FEATURE_REQUESTS.md`；等下一個 fleet 產品（如 tukey-* 系列或 ic-yms）出現「功能跨 sibling repo 拆分、需要契約優先」的情境時再抽，屆時可参考 spine-* 系列（`spine-schema-sync` 等）的「先驗證多產品收斂、再定 canonical + divergent 兩層」寫法。
