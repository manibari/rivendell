## Skill 候選

### 🟢 Strong：`git-branch-review`

- **用途**：隊友/協作者推了新分支後，系統性審查該分支的變更（`git fetch` → `git log`/`diff` 逐檔分析 → 影響範圍判斷），確認無誤後再合併拉下來。
- **Trigger**：「應該有人 push 一個新版」「review [分支名] 那條分支」「分析完再拉下來」
- **Category**：`git`
- **理由**：Session 4 用了 58 次 Bash（多為 git 操作）+ 8 Edit + 7 Read，橫跨前端（`FabDrawingPreview.tsx`）與 pipeline（`dwg_pipeline.py`、`geometry-pack.ts`）多檔案，是清楚的重複序列。現有 `git/` 目錄下的 `concurrent-session-git`（多 session 搶同一 working tree）、`repo-rename`、`auto-stage` 都不處理「審查他人分支再決定合併」這個動作，是明確空缺。

### 🟡 Moderate：`feedback-verification-report`

- **用途**：從 Google Sheet 讀客戶回饋列表，對照截圖/圖片座標標註（session 中出現「乘以 1.26 對應回原圖座標」這類具體換算），交叉比對程式碼位置，產出結構化驗證/待辦文件。
- **Trigger**：「這是使用者的回饋，跟我說一下」+ Google Sheet 連結 + 圖片附件
- **Category**：`quality` 或 `business`
- **理由**：Session 5 用了 123 次 Bash + Google Sheet MCP + 圖片裁切工具，流程明確可重複。但目前只有這一個樣本，且高度綁定 PTI-ARES 的 geometry engine 領域（`engine.py`、`preflight_closed_circles.py`），建議先觀察是否在其他專案也出現同款流程，再決定要不要抽成通用 skill，避免變成「只服務單一專案」的偽通用 skill。

### 🟡 Moderate：核定案例逆向比對（併入 `subsidy-writer`，非新 skill）

- **用途**：讀取一份「已核定通過」的舊補助計畫書 PDF，逆向分析其寫法規則（分項架構、經費配置、用詞），再與目前草稿逐項比對差異。
- **理由**：這個能力目前已有 `subsidy-writer` skill 覆蓋補助計畫書的生成端，Session 2 展現的是「用已通過案例做 precedent diff」這個子能力——**建議作為 `subsidy-writer` 的功能增強**，而非獨立新 skill。除非未來發現同一招在合約審查/標案審查等其他文件類型也重複出現，屆時再考慮抽成跨領域的 `precedent-diff` skill。
