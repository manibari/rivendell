## Skill 候選

### 🟢 Strong — Schema/Key 變更的唯讀影響面盤點（Migration Blast-Radius Audit）

- **名稱**：`migration-impact-audit`（建議新建，backend 或 quality 類別）
- **目的**：在動手改 schema / key 生成邏輯（如 `violation_key.py` 的 fingerprint 算法）之前，先寫一個**唯讀 scratchpad 腳本**（monkeypatch 新舊邏輯、對現有生產資料雙算），量化：
  1. 舊 key → 新 key 是否 1:1（有無 collision / one-to-many）
  2. 下游依賴表（如 `dispositions`）目前實際筆數是否為 0（沒有客戶資料需要救）
  3. 是否需要啟動保守協議（dual-key / alias table / 備份）——多數情況下量化後發現「窗口大開、一行修復即可」，原本規劃的複雜 migration 協議整組不需要
- **觸發**：要改動生產環境已在用的 key/fingerprint/schema 算法、且不確定影響面時；「這個改動要不要 migration」「先評估風險再改」
- **類別**：backend（或獨立於 quality）
- **理由**：這是本次 harvest 最高價值、最可複用的方法論——不綁定 ODB++/PCB 領域，任何「key 生成邏輯要換算法」的場景都適用（換 hash 演算法、換主鍵組成、換序列化格式）。現有 `db-migration`（設定 migration 工具）與 `spine-schema-sync`（Alembic 慣例）都不含「唯讀影響面盤點」這一步——他們假設「migration 要做」，本模式是回答「要不要做、做多重」。已 grep 確認兩者皆無 blast-radius / 唯讀模擬相關內容。

### 🟡 Moderate — Finding 風險分類：根因車道優於症狀覆蓋表

- **名稱**：`finding-risk-lanes`（可作為 `migration-impact-audit` 的參考章節，或獨立輕量 reference）
- **目的**：審查一批 findings/violations 時，先按**根因層級**分車道（A. 物理量測邏輯 bug——對所有輸入皆錯，用 vs. ground-truth 的 delta 當度量；B. 輸入慣例正規化缺口——用 corpus 軸覆蓋當度量；C. 產品信任/維運問題——與資料無關），而不是做「發現 × 覆蓋範圍」平表。平表會把 A 類（全域錯誤）誤標成「已覆蓋/低風險」，因為它在所有樣本上都觸發，看起來像「覆蓋完整」而非「邏輯必錯」。
- **觸發**：審查一批 bug/violation/finding 要排優先順序、且有「哪些樣本觸發過」vs.「這是不是全域邏輯錯誤」的混淆風險時
- **類別**：quality 或併入既有 review 類 skill
- **理由**：只在本次一組 session（同一輪審查）出現，樣本數較薄；且與 `migration-impact-audit` 常一起出現（本次兩份報告皆同一輪產出）。建議先以 Moderate 觀察，若下次 PTI-ARES 或其他專案的風險審查再次採用同一分類框架，再獨立成 skill；否則併入 `migration-impact-audit` 的「盤點前先分類」步驟。
