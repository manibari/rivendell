## Skill 候選清單

### 🟡 Moderate — canvas-pan-zoom-pattern（可縮放拖曳畫布互動模式）

- **用途**: 當畫面需要地圖/路網/關係圖/族譜樹等大型可縮放拖曳畫布時，提供一套可重用的互動狀態機規格（wheel/drag/pinch 手勢對映、縮放上下限、座標系轉換、慣性/邊界處理），輸出成 flow doc + 可互動 preview，再交給 `mockup` 產生 HTML。
- **觸發時機**: 使用者要求在畫面加入「可縮放拖曳的畫布 / 地圖 / 關係圖 / 路網視覺化」
- **涵蓋步驟**: 定義畫布座標系與縮放範圍 → 定義手勢對映（wheel/drag/pinch/慣性）→ 寫成 canvas-pan-zoom-flow.md → 交 `mockup` 產出可互動 preview → 沉澱互動邏輯（如 admission.ts 一類的狀態管理）
- **分類建議**: frontend
- **來源**: Session 2（PTI-ARES）完整跑過一次，產出 4 個對應檔案（flow.md / .md / preview.png / admission.ts），顯示這不是隨手一次性產物而是有結構的子交付
- **現有相似**: `mockup` skill 覆蓋「產出 UI mockup」本身，但沒有處理畫布手勢互動這個更技術性的子問題（座標轉換/縮放狀態機），兩者互補而非重複
- **理由**: 目前只有一次實例（n=1），建議先觀察 PTI-ARES 或其他地圖/路網類產品是否再出現同型需求，累積第二個實例後再抽 skill；在此之前可先把這次的 canvas-pan-zoom-flow.md 留在 PTI-ARES repo 內當 reference 供下次複製起手。

### 🟡 Moderate — multi-reference-zone-mapping（多分區外部參考對映）

- **用途**: 當一個產品有多個功能/氛圍迥異的畫面分區（如遊戲的外交/內政/軍事、或 SaaS 的儀表板/報表/設定），且使用者是用「這塊像 X 產品、那塊像 Y 產品」的方式描述需求時，系統化地把每個分區各自的參考來源、映射程度（純美術 vs 含互動邏輯）記錄進 DESIGN.md 對應 section，避免全站套用單一 design system 導致風格衝突或映射遺漏。
- **觸發時機**: 使用者提供多張截圖並描述「A 畫面像 X，B 畫面像 Y」這類分區式參照
- **涵蓋步驟**: 收集所有參考截圖 → 逐分區 AskUserQuestion 確認映射意圖與程度 → 寫入 DESIGN.md 對應分區 section → 交給 `mockup` / `frontend-design` 產出
- **分類建議**: frontend
- **來源**: Session 1（MingOS），10 msgs，2 次 AskUserQuestion 皆用於釐清分區映射
- **現有相似**: `chimesflow-design` 是單一 SoT 全站錨定；`ui-ux-pro-max` 是風格資料庫查詢；`gstack-design-consultation` 產出單一完整設計系統。三者都假設「一個產品一套風格」，沒有處理「同產品內多分區各自映射不同外部產品」的混合情境
- **理由**: 目前僅一次實例、僅 10 則訊息，複雜度偏低（AI 主要靠 AskUserQuestion 澄清，沒有展現大量步驟或專門領域知識）。是否值得獨立成 skill 存疑——MingOS 是遊戲類專案，這類「分區各自參照不同遊戲」的需求可能會在後續開發中重複出現，但目前證據不足以判定為 Strong，建議先觀察 MingOS 是否有第二次類似分區設計需求再決定。
