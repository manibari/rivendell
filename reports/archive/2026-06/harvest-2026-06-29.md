## Skill Candidates

### 1. `api-key-auth`（service-to-service API 金鑰認證）— **Moderate**

- **Purpose**：為 FastAPI / 爬蟲後端加上 API key 認證層 —— 金鑰產生（含 prefix + 隨機亂數）、雜湊儲存（不存明文）、`X-API-Key` header 驗證 dependency、金鑰輪替與撤銷。前端帶 key 呼叫、後端做最小改動接入。
- **Trigger**：使用者要「做一個 API key 的功能」「給爬蟲/資料 API 加保護」「前端帶 key 呼叫後端」「服務之間要認證但不是登入帳號」。
- **Category**：backend
- **Rationale**：
  - Session 1 明確出現「我直接做一個 api key 的功能，你這邊的 backend 可能也要小修改一下」，且實際動到 `.env.example`、`main.py`、`README.md`，是完整的一個 feature。
  - **與既有 skill 有真實 gap**：`spine-auth` 是使用者 JWT 登入（jose + bcrypt + Bearer），`oauth-token-vault` 是第三方 OAuth token 保管，`rbac-permissions` 是角色分權。**沒有任何 skill 處理「機器對機器、單一共享金鑰、X-API-Key header」這個 pattern** —— 這是 scraper / data API 最常見的保護方式，與帳密登入是不同軸線。
  - 屬於 fleet infra spine 的潛在新模組（多個爬蟲/資料服務都會用到），可與 `spine-auth` 並列為「auth 的另一條 lane」。
  - 評為 Moderate 而非 Strong：目前 n=1，需再觀察 1–2 次跨專案重現（pti-ares / mops admin / ic-yms 任何資料 API）再升級 / 抽 spine 模組。

### 2. `decouple-hardcoded-identity`（解除 hardcoded 單一使用者耦合）— **Weak**

- **Purpose**：系統性盤點並移除程式碼中寫死的個人/開發者身分（如帳號名、個人路徑、單租戶假設），改為設定驅動 / 多租戶可擴展。產生「耦合點清單 → 逐點解耦 → 驗證」的 checklist。
- **Trigger**：「把 X 這種耦合極高的東西處理掉」「移除寫死的帳號/使用者」「從單一使用者改成多使用者」。
- **Category**：quality（refactor）
- **Rationale**：
  - Session 1 出現「先把 jacktsai 這種耦合極高的東西先處理掉」—— 是一個可辨識的重構 pattern（de-hardcode developer-specific identity）。
  - 與 `repo-rename`（跨位置 reference 稽核）形神相近但對象不同（身分 vs repo 名）。
  - 評為 Weak：n=1、範圍偏窄，且實作大半可由通用 refactor 直接處理，不一定值得獨立 skill。先記錄，若再出現第二次（任何「單人工具 → 多人化」）再考慮，符合「2+ 次重現才升級」原則。
