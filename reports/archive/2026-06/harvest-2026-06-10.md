## Skill 候選

### 🟢 Strong — `phm-soft-sensor`（PHM 軟儀表 / 設備健康度監控）

- **Purpose**：把廠務時序資料（UPW/RO、壓縮機、冷凍機等）轉成**軟儀表（虛擬量測）+ 健康度指標 + 異常檢測**的監控儀表板。內建兩層建模法：**fleet-pooled baseline 先開工 → 各機台 fine-tune**；輸出**雙受眾版面**（工程師時序細節 vs 主管切分頁概覽）。
- **Trigger**：「軟儀表」「健康度監控」「效能監控」「異常檢測」「PHM」「設備劣化」「soft sensor」「health index」。
- **SKIP**：一次性 CSV→PPTX 廠務報告（用 `iot-factory-report`）；純表格資料 dump（用 `office-xlsx`）。
- **Category**：`workflow`（或 `docs`，因含 dashboard 產出）。
- **Rationale**：
  - 跨兩個 session 重複出現一套**多步工作流**：(a) 建 baseline 模型 → (b) 算殘差/健康度 → (c) 標異常 → (d) 雙受眾視覺化 → (e) 截圖驗證重做。Bash+Edit+Read 高頻交替正是「建模→驗證→調整」迴圈的指紋。
  - **領域知識值得固化**：fleet-pooled vs per-machine 的取捨、健康度指標（殘差/偏離 baseline）作為非工程師可讀的單一指標、「機台先順序執行再平行」的工程節奏——這些都是 user 親自下的決策，不是通用常識。
  - **明確區隔於既有 skill**：`iot-factory-report` 是一次性 CSV→靜態報告+PPTX；本案是**可迭代的監控儀表板 + 軟儀表建模**，產出 `.py` + live dashboard 而非單份 deck。兩者領域相鄰但流程不同。
  - 與 user CLAUDE.md 既有偏好相容：「主管版/工程師版分流」「截圖自我驗證」已是反覆踩坑的規則，本 skill 把它收斂成設備監控場景的固定流程。

### 🟡 Moderate — `dashboard-dual-audience`（雙受眾儀表板版面）

- **Purpose**：同一份資料產**兩種版面**——工程師版（含技術指標、時序細節）vs 主管版（切分頁、隱藏技術名、單一健康燈號）。標準化分頁結構與資訊密度取捨。
- **Trigger**：「主管版/工程師版」「切分頁」「給長官看的儀表板」「executive dashboard」。

- **Rationale**：Session 1「主管版用切分頁」+ Session 2「不是工程師常看的圖，用時序+健康度說明」是同一條需求的兩面。但**此模式已大量散落在 user CLAUDE.md「長官/委員/CIO 版要分流」規則中**，且與 `frontend-design`、`chart-design` 重疊。建議**先當 `phm-soft-sensor` 內的一個 section**，累積到第 3 個非 PHM 案例再抽獨立 skill。降為 Moderate 即因尚未證明跨領域複用。
