- **pull 前風險評估（這段最有價值）**：
  - `git diff --name-only HEAD..@{u} | grep -E 'next.config.ts|pnpm-workspace.yaml|.npmrc|package.json|pnpm-lock.yaml'` — **upstream 有沒有動到我本地也改過的檔案**

  - `git show @{u}:CHANGELOG.md` / `git ls-tree --name-only @{u}` — **先讀 upstream 的 CHANGELOG 和目錄樹，再決定要不要動 schema/seed**
  - `git diff --name-status HEAD..@{u} | grep -iE 'compose|dockerfile|serve\.sh|cloudflared|\.env|deploy'` — **部署契約檔有沒有變**
- **長時部署的背景化**：`setsid bash -c './scripts/serve.sh update > <scratchpad>/pti-updateN.log 2>&1' < /dev/null &`，再用 `until grep -qE 'pti-ares status|build failed|git pull failed' <log>; do sleep 5; done` 等收斂
- **殘留行程清理**：多次出現 `pgrep -af "serve.sh update"` 找到**上一輪沒死乾淨的 wrapper**、`ps -o pid,sid,cmd` 分辨 server 與 wrapper、`kill` 掉孤兒後重驗 port
- **`/rulecheck` 掛掉的四層排除法**：
  1. **邊緣層**：`curl` 公開網域 + 靜態 chunk → `docker logs pti-ares-cloudflared` 找 `control stream encountered a failure` → 比對**其他 5 個專案的 cloudflared 容器**錯誤率 → `docker restart` + `until ... grep -c "Registered tunnel connection"` 等 4 條連線回來 → 連打 10 次 curl 確認不是 tunnel 問題
  2. **應用執行層**：`gstack browse` 登入（`. .localdata/serve.env` 取帳密）→ `goto` → `console` / `network --clear` 抓真實錯誤 → 從 DOM 撈 Next.js `digest`
  3. **本地重現**：`setsid ... next dev -p 3099` **開一台 dev server 打正式 backend**，把 minified digest 換成可讀 stack trace ← **本 session 的關鍵破案手法**
  4. **資料層**：`docker exec pti-ares-db psql -tAc "select ... jsonb_array_elements(content->'rules') ..."` 確認是**草稿規則的 `spec` 為 null** 導致 `ruleTypes[r.spec.type]` 爆炸
- **修復與收尾**：前端加守衛 + 後端 `library.py` 建草稿時保留 `spec:null` + 補 `tests/test_rule_library_edit.py` → 版號 bump → push → 再跑一輪 `serve.sh update` → 用 browse 讀側邊欄 badge 確認線上真的換版
- **版號 bump 踩到的坑**：改了 `pyproject.toml` + `src/pti_app/__init__.py` + 兩份 `CHANGELOG.md` 後，**漏掉 `backend/data/roadmap.json`**（側邊欄 badge 的實際來源），只好補一個 `chore(version)` commit
