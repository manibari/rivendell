## Skill 候選

### ⚪ Weak 觀察值 1 — `rbac-drift-check`（commit 後權限 drift audit + scenario test 編號制）

- **purpose**：實作 RBAC 變更（新增 role / 跨部門讀寫 / endpoint 保護）並 commit 之後，自動做一次「權限矩陣 drift audit」：
  1. 對 commit 前後跑同一份 role × endpoint 全表快照，diff 出意外增/減的存取行（找意外打開或鎖死的權限）。
  2. 強制要求對該變更寫一支編號 scenario test（`cross_dept_<role>_<NNN>.py` 編號制），跑回歸。
  3. 輸出 audit 報告（哪些 endpoint 因這次 commit 改變了存取性、誰會受影響）。
- **trigger**：「commit 後權限有變動嗎」「跑一次 RBAC drift check」「permission audit after change」「跨部門新權限 + 寫對應測試」。
- **SKIP**：純認證（無 role 差異）；新建 RBAC 系統第一次設計（用 `rbac-permissions`）。
- **category**：backend / quality
- **rationale**：
  - **使用者反射動作**：ChimesFlow session 結尾使用者主動問「目前的權限管理有變動嗎」→ 這是一個值得編碼的習慣動作。
  - **編號制證據**：`cross_dept_read_001.py` 的 `_001` 後綴是強訊號（之後必有 002、003）。
  - **既有 skill gap**：`rbac-permissions` 教**怎麼設計 RBAC**，**沒有教 commit 後怎麼 audit**。`qa-testing` 是通用 QA 不含 RBAC 特定 drift 分析。
  - **為何只給 Weak**：只在 ChimesFlow 一個 session 出現一次，且 ChimesFlow 是內部 ERP/CRM，這個 audit 動作可能是該專案 in-house convention，不是跨專案通用流程。先觀察是否在其他全棧專案（dashboard-next、Nexus 等）重現。

### ⚪ Weak 觀察值 2 — `monthly-codebase-state`（月度 codebase 三件套）

- **purpose**：每月初生一份「state-of-the-codebase-YYYY-MM.md + next-wave-YYYY-MM.md + rule-framework.md」三件套：
  1. **state-of-the-codebase**：codebase 現況快照（line count、模組地圖、技術債清單、上月 commit summary）。
  2. **next-wave**：本月優先級 roadmap（從 backlog 抽 top-N、附 success metric）。
  3. **rule-framework**：本月有效的 engineering rule / convention 集合（覆蓋本月計畫的決策邊界）。
- **trigger**：「做月度 codebase 報告」「state of the codebase」「下個月做什麼」「next-wave roadmap」、`-YYYY-MM.md` 檔名模式偵測。
- **SKIP**：一次性需求釐清（用 `requirement`）；engineering retro（用 `gstack-retro`）。
- **category**：meta / workflow
- **rationale**：
  - **cadence 證據**：檔名帶月份戳，暗示重複 cadence。
  - **既有 skill gap**：`requirement` 是通用需求文件、`writing-plans` 是實作 task list、`gstack-retro` 是 commit history 回顧，**沒有整合「現況 + roadmap + rule」三件一組的月度節奏**。
  - **為何只給 Weak**：只有 2026-05 一份，無法判斷是否會 recurring。**6 月若出現 `*-2026-06.md` 同型檔，立即升 Moderate 並用 `skill-creator` 建。**
