## Session 拆解

### [1] odb-dfm：DXG↔ODB++ 座標配準 + 元件 footprint 渲染 + 前端預覽（163 msgs，Bash×92 / Edit×31 / Read×21 / Write×9）
- **意圖軌跡**：「mounting hole landmark 配 H 軸」→「**可以先有前端畫面讓我看一下嗎？不然你做到什麼程度我都不知道**」→「component 沒有看到 pin 腳、極性點等等，還是這是未來的計劃」。
- **產出**：`dxg_register.py`（DXG fab drawing 座標系 → ODB++ 板座標系的 landmark 仿射配準）、`footprint.py`（pad-first 實體元件模型，body+pads+pin-1 為一個物件，依板面強制鏡像修正翻轉）、register view 前端視覺化。
- **領域知識（已寫進 module docstring）**：
  - 兩套圖（fab drawing DXG vs 板模型 ODB++）座標系不同：PB0009 是 90° CW、scale 1.0、無鏡像。
  - **壞 landmark 拒絕法**：先試 mounting/datum hole（直覺選擇）→ 第三孔落不進 ~12 mm → 拒絕；改用「乾淨全寬邊（未帶 tab 的那條長水平邊）」當 H 軸 anchor，避開 bridge tab 突出 ~5 mm 造成的 ~14 mm 殘差污染。
  - **配準後一定要 verify guard**：把偵測到的 bridge 反映射回 ODB++ mm，檢查是否落在板邊 → 任意板的驗收測試。
- **行為回饋訊號**：使用者**兩次**抱怨「看不到進度 / 看不到 pin 腳極性點」→ 後端跑很久卻沒有可視中介產物，使用者無法追蹤。這是一條**行為 feedback**（早點給可視預覽），不是 skill。

### [2] odb-dfm：sandbox PoC → 多租戶產品 重構（332 msgs，Bash×153 / Edit×64 / Read×39 / Write×20 / AskUserQuestion×14）
- **意圖**：「這個產品已經引起客戶的興趣，需要 refactor 成產品」+ 明確列出 pipeline：讀 ODB++ → 解析成 JSON → 建面板/元件/極性點 → rule 模組 → rule check。起手呼叫 `requirement` skill。
- **產出**：從 vault `scripts/odb-dfm/` 沙盒抽 11 個腳本 → `src/odb_dfm/` package、CLI entry points（`parse/checklist/enrich/check/visualize/export/search/all`）、`Paths.from_client()` 客戶路徑注入、smoke pytest、`docs/requirements/productization.md` 三階段範圍。
- **核心方法學（可複用，見下方候選）**：
  - **硬綁地雷盤點**：`parser.py:13` 客戶路徑硬綁、`:26` 板名硬綁、`checklist.py` 綁死舊版分頁名（V3 已 break）、`RULE_HANDLERS` key 綁死 PTI 的 CP 編號 → 客戶換 checklist 版本就崩。
  - **第二資料集 dry-run 逼出耦合**：用 PB0009（第二塊板）跑既有 v0.1.0 pipeline，當場炸出 `KeyError: 'Worksheet Summary does not exist.'`（規則 taxonomy 隨 checklist 版本變，非只隨客戶變）→ 把隱性耦合變成可規劃的 US-2/US-3。
  - **codex outside-voice 修正**：codex review 用 code-grounded 證據挑戰 Phase 1 計畫，抓到 `seen_pairs` 誤診（不是 geometry dedup，是 component-pair dedup）、scope overbuild 等 6 點 → 計畫修正。

## 跨 session 模式分析

1. **PoC → 產品化是使用者的核心商業循環**：odb-dfm README 寫明「種子客戶力成 → 產品化 → on-prem 授權任何做 PCB DFM 的組織」。使用者的顧問式生意本質就是「客製 PoC 驗證 → 抽成產品賣多家」。session [2] 是這條循環第一次被 harvest 到的完整實例 → 值得沉澱方法學，但僅 1 次 → **Moderate 而非 Strong**。
2. **絕大多數工程是領域特定**：ODB++ 解析、DXG/DXF 抽綠 hatch、Valor 相容、座標配準 — 換到非 PCB/CAD 專案幾乎不重用。可複用的只有「方法學外殼」（負債盤點、壞 landmark 拒絕、第二資料集 dry-run），不是領域實作。
3. **無「A→B→C ≥2 次」的跨 session 新 workflow**：兩個 odb-dfm session 是同一產品的連續推進，不是兩次獨立重複同一序列。
4. **「看不到進度」回饋 + AskUserQuestion×14**：使用者在長後端任務中反覆要求可視中介產物。這指向一條**行為準則**（長 pipeline 工作要早交付可視 checkpoint），更適合 feedback memory / CLAUDE.md，不是獨立 skill。

## Skill 候選

### 🟡 Moderate — `poc-to-product-audit`（產品化負債盤點）
- **purpose**：把一份「給單一種子客戶跑通的 PoC / 沙盒腳本集」盤點成可多租戶交付的產品前，系統性找出阻擋產品化的硬綁地雷，並用「第二客戶資料集 dry-run」逼出隱性耦合，輸出分階解耦 roadmap。流程：(1) grep 硬綁路徑/客戶名/板名/版本綁定的分頁名/客戶專屬 ID；(2) 不改 code，拿第二個客戶/資料集跑既有 pipeline，記錄每個 stage 在哪裡崩（崩點即耦合點）；(3) 把崩點翻成 user story（路徑注入、rule identity 解耦、版本 adapter）；(4) 排 Phase（地基正確性 > 設定債 > 能力擴充）。
- **trigger**：「把 PoC 產品化」「這個沙盒要變產品」「要支援多客戶 / 多租戶」「sandbox → package」「客戶要採購了，要 refactor 成產品」「on-prem 授權」。
- **SKIP**：全新專案無既有 PoC（用 `requirement` / `init-project`）；純檔案結構模組化（用 `large-file-refactor`）。
- **category**：meta（偏 workflow）
- **rationale**：使用者整個顧問生意都是這條循環，session [2] 是首個完整實例。**無既有 skill 覆蓋**：`init-project` 只建 CLAUDE.md/AGENTS.md、`requirement` 只定義通用範圍、`large-file-refactor` 只做結構拆分、`github-repo-audit` 是 repo 健檢非產品化耦合盤點。本 session 證明過的差異化價值是「**地雷盤點 + 第二資料集 dry-run**」這套方法 — 一次同時炸出客戶路徑、板名、checklist 分頁名、rule ID 四種耦合。評 Moderate（僅 1 次出現，待第二個客戶產品化案再升 Strong）。
