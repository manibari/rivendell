## Strong：`fmcs-tag-pivot`

- **Purpose**：把 SCADA / FMCS 匯出的「長表」原始 CSV（一行一個 `(timestamp, tag, value)` 或多 tag 同欄混雜）pivot 成「寬表」（時戳 × 設備點位 column），供後續 iot-factory-report 直接消費。包含 tag 命名清洗（如 `RO-01.PT-101.PV` → `RO01_inlet_pressure`）、缺值補齊策略、單位換算、時戳對齊。
- **Trigger 條件**：
  - User says「資料預處理」「FMCS 點位」「先把 CSV 整理好」「raw CSV → 寬表」
  - 偵測到 CSV 欄位含 FMCS / SCADA tag 命名特徵（`PT-`, `TT-`, `FT-`, `.PV`, `.SP`）
  - iot-factory-report 觸發但輸入 CSV 不是寬表 → 自動前置呼叫
- **Skip 條件**：CSV 已是寬表（office-xlsx 即可）；非工業點位資料。
- **Category**：`docs/`（與 iot-factory-report 並列）或作為其 `_preprocessing/` 子模組。
- **Rationale**：
  1. Session 1 用了 132 次 Bash + 63 次 Write，幾乎全部花在資料整形（FMCS column 對齊、建新資料集），現有 `iot-factory-report` skill 從 Step 1 即假設輸入是乾淨的時序寬表 → 預處理是隱含步驟，使用者每次都要自己摸索。
  2. FMCS tag 命名與單位換算是強領域知識，下次遇到不同設備一定再用。
  3. 與 `office-xlsx` 的差異：office-xlsx 是通用 Excel/CSV 操作；本 skill 專注「FMCS/SCADA tag dictionary → standardized column」這層 domain mapping。

## Moderate：`iot-baseline-snapshot`

- **Purpose**：給定一段「正常運行」期間的設備時序資料，產出 baseline snapshot（key metric 的 P10/P50/P90、cycle 平均、效率曲線），存成可版本化的 JSON/markdown。後續資料進來時，自動 diff against baseline 並產出 deviation 報告（PHM 預警的入門版）。
- **Trigger**：「設備 baseline」「PHM baseline」「效率基線」「跟上次比有沒有退化」
- **Skip**：單次分析（用 iot-factory-report）；異常偵測需要 ML 模型（超出 scope）。
- **Category**：`docs/` 或 `workflow/`。
- **Rationale**：
  1. Session 1 產出了 `2026-05-08_efficiency_phm_baseline.md`，明確是把當前資料當基線存起來，意圖讓未來資料能比對。
  2. iot-factory-report 是「一次性報告產生器」，沒有 baseline 持久化的概念。Baseline workflow 是值得獨立的「狀態管理」pattern。
  3. 評為 Moderate 而非 Strong：只看到一次使用，不確定是否會反覆出現（也可能就 SDP 一個客戶的事）。建議先觀察 1-2 次再決定是否 codify。
