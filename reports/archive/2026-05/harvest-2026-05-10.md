### Moderate (值得觀察，再多 1-2 個 session 樣本就建)

#### 候選 1：`headless-error-triage`

- **Purpose**：當排程的 headless agent（如 crm-projection、material-health、subsidy-scraper、tender-scraper）在執行中遇到非預期錯誤時，統一寫入 `.learnings/ERRORS.md` 並判斷是否要在下一輪重試或升級為人類介入。
- **Trigger**：headless agent 執行中遇到 (a) skill 內部斷裂 (b) 外部資料源回 4xx/5xx (c) AskUserQuestion 在 headless 模式下被觸發（不該發生）。
- **Category**：`meta/`（橫跨多個排程 skill 的錯誤治理）
- **Rationale**：
  - Session 4 出現 `ERRORS.md` 被修改 + headless 流程中跑出 `AskUserQuestion×1`。後者是異常訊號 —— 排程 agent 不該停下來問問題。
  - 既有 `self-improving-agent` 處理「人在迴圈中」的學習記錄；`headless-agent` skill 教如何啟動 headless 流程。但兩者中間缺一個「排程跑 → 失敗 → 分流（重試/降級/升級）→ 寫 ERRORS.md」的標準化收斂機制。
  - 訊號不夠強，因為只在一個 session 看到。但跨 skill 痛點明顯，下次再看到類似 pattern 就值得做。

#### 候選 2：`continuous-research-daily-report`（弱 Moderate）

- **Purpose**：抽象化「每日寫一份 daily-YYYY-MM-DD.md → 更新 state.json → 投資/監測類 agent 通用」的骨架，讓 investment-research、tender-scraper、subsidy-scraper、material-health 共用同一套日報格式與 archive 規則。
- **Trigger**：使用者要建立一個「每日跑一次、寫日報、維護 state」的新 agent。

- **Rationale**：
