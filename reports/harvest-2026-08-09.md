### 🟢 Strong：`deploy-effect-verification`（部署生效驗證）

- **Purpose**：重新部署一個既有的自架服務之後，**證明正在跑的 process 真的是新版程式碼**——而不是拿 exit 0 當結論。兩段：(a) 找到專案自己的部署入口（而不是自己重組 pull/build/restart 步驟）；(b) 跑完之後逐項舉證生效或明確判定 no-op。
- **Trigger**：
  - 「pull & rerun」「重新部署」「更新一下」「部署上去」這種**動詞含糊、沒有指名腳本**的維運要求
  - 部署腳本跑完了，但畫面／版本號／行為沒變
  - merge 或 push 之後要確認 prod 到底吃到沒
  - 有 cron／自動更新機制的專案，要判斷「已 push」與「已部署」之間的落差
- **Category**：`workflow/`
- **Rationale**：
  - **n≥4，橫跨 3 個專案，而且每一次的失敗模式都不同**：
    - **ChimesFlow（session 1）**：`chimesflow-redeploy.sh` 三步全綠。但 `git pull` 的 19 行 `* [new branch]` 只是首次 fetch 遠端 ref，**不是新 commit**（極易誤讀成「拉到東西了」）；docker layer 全 CACHED、容器仍是 `Up 32 hours` 代表沒有被重建；`alembic upgrade head` 無 migration。**這四項舉證全都不在腳本裡**，是事後自己補的。
    - **mops-dbs（08-07 同專案）**：merge 進 `v0.18.0` 之後，**不另外 build 前端，`dist/` 就還是舊的**，restart 也沒用；最後靠 `release.py` 的版本號從 0.17.5 翻到 0.18.0 才算數。
    - **mops-dbs 的 cron 自動部署**：`deploy/local/autoupdate.sh` 每 5 分鐘跑，但**爬蟲執行中時會 defer restart（≤1/hr）**，所以「push 完了」跟「prod 在跑新版」之間有最長一小時的空窗；而且**工作目錄一髒就整個 ff-pull 卡住**（實際卡了 10:00–10:20）。
    - **pti-ares（`harvest-2026-08-02.md` session 23）**：「不 rebuild 前端渲染畫面不對」——同一類，第三個專案，獨立長出來。
  - **既有 skill 沒有一支接得住**：`deploy` 是**綠地**——「recommend deployment platform and generate deploy config（Dockerfile / fly.toml / vercel.json）」，講的是第一次怎麼配起來；`ci-pipeline` 是 CI；`docker-compose-setup` 是初次容器化；`cloudflare-tunnel-ops` 只到網路層；`qa-*` 測的是應用行為，不問「跑的是哪一版」。**「既有服務的第 N 次部署」目前是空的。**
  - 探測手法本身有非直覺的細節值得寫死：容器裡不見得有 `curl`，要用 `docker exec ... python -c "import urllib.request"` 打 health；`alembic current` 要補 `-e PYTHONPATH=/app` 才跑得動；`docker images --format '{{.CreatedSince}}'` 比 `docker compose ps` 更能分辨「有沒有真的重建」。這些是 session 1 逐次試錯試出來的。
- **建議結構**：

  - `references/noop-signatures.md`：`Already up to date` vs `* [new branch]` 的差別、docker layer `CACHED`、容器 uptime 未歸零、`dist/` mtime 早於 HEAD commit、alembic 版本未動
  - `references/staleness-traps.md`：前端 build 產物要另外重建、cron 自動部署的 defer 與 dirty-tree 阻塞、多份 unit（repo 版 vs 已安裝版）漂移

### 🟢 Strong：`external-storage-tiering`（資料分層搬遷到外接／慢速掛載）

- **Purpose**：把體積大、可重新取得、寫一次少讀的資產（檔案快取、DB snapshot）從內部快碟搬到外接碟或慢速掛載，過程中**不弄壞任何正在讀它的程式**。含：可搬性判定 → 真實路徑探測 → 複製 → 校驗 → symlink 切換 → 設定同步 → 事後陷阱。
- **Trigger**：
  - 「空間不夠」「搬到外接硬碟」「存到 E 槽」「cache 太大」
  - 資料目錄要換位置，但有 container / systemd / 排程在讀它
  - `du` 或 `find` 對某個目錄回報 0 但檔案明明在
- **Category**：`workflow/`
- **Rationale**：
  - **session 3 完整跑了一遍，每一步都有非直覺的理由**，而且順序不能換：
    1. **先探測真實路徑，不讀設定檔**。`PDF_CACHE_DIR` 在 `ebook_sync.py:27`、`bulk_f17_download.py:29`、`viewer.py` 各有一套 fallback，最後是從**容器內部** `docker exec ... python -c` 把實際解析結果問出來的。
    2. **rsync 之後用 `rsync -rnc` dry-run 做 checksum 比對**，零差異才動原目錄（1,922 檔 / 379,919,285 bytes 全對）。
    3. **`mv` 成 `.old` 而不是 `rm`**，symlink 建好、讀得到之後才算完成。
  - **踩到的陷阱有兩個是 n=2，且其中一個差點造成實害**：
    - **symlink 讓 `find` / `du` 說謊**：`~/mops_databases/xbrl_cache` → `/mnt/e/mops_cache/xbrl`，`du` 回 0、`find` 找不到，但 `ls` 看得到、`os.walk` 讀得到 26,422 個 `.gz`。**08-07 那場差一點就對「看起來是空的」cache 發動 reparse**——那正是該專案 SoT 明文警告的「silently empty」情境。
    - **docker bind mount 不能掛 host 的 symlink**：容器內解不到目標，compose 必須改掛真實路徑（session 3 的 compose 編輯正是為此）。
  - **效能估算要換公式**：`/mnt/e` 是 DrvFs／9p，成本由**檔案數**主導而非總量。同一份 xbrl cache 的 walk，從開發機的 9 分鐘變成這台的一小時以上（26k 檔 vs 9k 檔 ＋ 跨 mount）。用「總量 ÷ 頻寬」估會低估一個量級。
  - **機器專屬設定要走 systemd drop-in，不進 repo**：session 3 把 snapshot 路徑寫進 `~/.config/systemd/user/mops-pg-snapshot.service.d/local-e-drive.conf` 並註明「勿進 repo：prod 沒有 E 槽」。這條和 08-07 發現的「repo unit 寫死 `PG_PORT=5441`、prod 實際是 5432」是同一個教訓的正反面。
  - **可搬 / 不可搬的判準是知識，不是常識**：cache 與 snapshot 可以（寫一次、少讀、可重新產生）；`pgdata` 不行（隨機寫 ＋ fsync 語意）——session 3 明確把 pgdata 留在 ext4。
  - **既有 skill 不覆蓋**：`env-doctor` 是 runtime 環境探測、`docker-compose-setup` 是初次容器化、`sqlite-to-postgres` 是資料庫層搬遷、`agent-observability` 是可觀測性。沒有一支處理「檔案資產換家」。
- **建議結構**：
  - `SKILL.md`：可搬性判定 → 真實路徑探測 → 複製 → 校驗 → 切換 → 設定同步 → 驗證
  - `references/what-can-move.md`：cache／snapshot／artifact 可搬；pgdata／WAL／SQLite／active log 不可搬，附理由
  - `references/symlink-blind-spots.md`：`find`/`du` 預設不跟隨（`-L` / `du -L`）、docker bind mount 解不到、`ls` 與 `os.walk` 會跟隨——含最小重現指令
  - `references/slow-mount-estimation.md`：DrvFs／9p／NFS 以檔案數計時的估算法與實測數字
  - `checklists/cutover.md`：`.old` 保留期、rollback 步驟、要同步的設定清單（env / compose / systemd drop-in / 排程）

### 🟡 Moderate：`rust-wasm-no-toolchain`（無 C toolchain 的 Rust→wasm）

- **Purpose**：在沒有 C compiler、也不想引入 npm／wasm-bindgen 生態的機器上，把純運算的 Rust crate 編成瀏覽器可直接載入的 wasm。
- **Trigger**：要把運算核心放進瀏覽器、`cargo build` 因缺 linker 失敗、想避開 wasm-pack／npm 這層工具鏈
- **Category**：`backend/`
- **Rationale**：
  - **知識密度高且全部在 session 2 被驗證過**，每條都是繞過障礙時得到的：
    - 機器沒有 `cc`／`gcc`／`clang` → **host target 連不了，但 `wasm32-unknown-unknown` 用內建 rust-lld 所以編得過**。推論是：`cargo test` 不能用，測試必須改成 node 跨 wasm 邊界跑（session 2 的 `test/smoke.mjs` 就是為此存在，而且**真的抓到 bug**——固定煞車餘裕讓車永遠卡在站前 12 公尺）。
    - **跳過 wasm-bindgen／wasm-pack／npm**：`crate-type = ["cdylib"]` ＋ `alloc_f64` 交換緩衝 ＋ JS 端 `WebAssembly.instantiate`，每幀從 wasm memory 零複製讀出座標。邊界只傳數字，本來就不需要膠水產生器。產物 82 KB、17 個 export。
    - **不裝 wabt**，直接用 python3 掃 wasm export section 確認符號有出來。
    - wasm 必須走 `http://` 載入，`file://` 會被瀏覽器擋——所以 `run.sh` 一定要起靜態伺服器。
  - **保留意見**：**n=1**，而且離主線（維運／資料管線／簡報）很遠。`railsim` 是興趣專案，未必有第二次。
  - **建議**：先寫成 `.learnings/` 一則（成本 10 分鐘），**第二個專案再碰 wasm 才 promote 成 skill**。這條刻意不列 Strong。
