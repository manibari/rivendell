## 三、用到的領域知識

- **docker compose 插值坑**：`env_file` 的值會被插值，scrypt / bcrypt hash 的 `salt$digest` 會被吃掉 → 需 `$$` 或改走別的注入路徑。兩個 session 都撞到。
- **single-origin 部署契約**：FastAPI mount 前端 dist 在 `/`，session cookie 免 CORS、tunnel 只需一個 upstream。
- **fork 不代表版本新**：IC-YMS 的 `upstream/master` 比 fork 的 `master` 更舊，真正要部的 `v2` 領先 master 65 commits。
- **Verdandi/Tukey registry 契約**：`X-API-Key` header、`/registry/models`、`/registry/versions/{id}/api-key`、`/projects/datasets/{id}/latest-run`；24 個倉別模型逐一登錄。
- **celery 併發**：`concurrency=1` vs `2` 直接決定總訓練時間，`running: 1 / 36 queued` 不是機器慢。
- **WSL ↔ Windows 資料交接**：使用者的資料包固定落在 `/mnt/c/Users/peter/Downloads/`，以 `-v "$D":/in:ro` 掛進容器處理。
- **預測模型輸給 naive 的排查順序**：先確認回測天數（實際只跑了 1 天）→ 再確認資料對齊（60P/60F 中途改名、品號前導零）→ 最後才談重訓。

## 四、技能候選

### 🟢 Strong

#### 1. `wsl-fleet-deploy`
- **用途**：把一個既有 repo 上線到本機 WSL2 prod 艦隊 —— 埠位分配、補部署層、健康收斂、資料 bring-up、cloudflared named tunnel、pull-deploy timer、寫 runbook memory，一條龍。
- **觸發**：「部署 X 到這邊」「上線到 *.phyra.uk」「deploy to this box」「加一個 auto-deploy」；或偵測到 repo 的 compose 只有 DB service 卻要上線。
- **不觸發**：雲端 PaaS 部署（用 `deploy`）、只是本機 dev 起服務。
- **分類**：`workflow/`
- **理由**：3/3 session 完整重跑同一條線，477 次 Bash 裡大半在此。艦隊已有 6 個 app、5 份 runbook、5 支 poller script，卻沒有任何技能承載。既有技能只覆蓋切片（`docker-compose-setup` 建 compose、`cloudflare-tunnel-provision` 開 tunnel、`cloudflare-tunnel-ops` 修 tunnel），**沒有一支負責編排全流程**，也沒有處理最痛的兩件事：**跨專案埠位分配**（session 1 就撞到 IC-YMS v2 預設的 8400 已被 iihi 佔用）與 **pull-deploy poller + systemd timer**。這支應該當 orchestrator 去呼叫既有的三支，而不是重寫它們。

#### 2. `gh-token-triage`
- **用途**：GitHub 存取失敗的分層排查 —— 分辨「repo 不存在 / token 沒權限 / fine-grained PAT allowlist 沒包含 / 環境變數蓋掉 hosts.yml / 該走 SSH 而非 PAT」，並給出對應修法。
- **觸發**：`git clone` 或 `gh` 對私有 repo 回 404/403、「換一個有完整權限的 token」「把 repo 加進允許清單」「gh 看不到我的 repo」。
- **不觸發**：第三方服務的 OAuth token 儲存（用 `oauth-token-vault`）。
- **分類**：`git/`
- **理由**：2/3 session 遇到，且都燒掉可觀的 turn 數；session 2 還因為判讀錯誤被使用者當面糾正。艦隊 memory 裡另有 `iihi` 註明「private — clone over SSH not gh PAT」，代表同一台機器上**不同 repo 走不同認證路徑**，靠記憶很容易搞混。`git/` 目前只有 `auto-stage` 與 `repo-rename`，這是明顯空缺。

### 🟡 Moderate

#### 3. `deploy-smoke-verify`
- **用途**：部署後的標準冒煙驗證 —— 健康狀態收斂輪詢、容器內 env 實際值、未登入期望 401、cookie jar / Bearer 登入、打真實資料端點確認有列、必要時用 gstack 開實際頁面截圖。
- **觸發**：`docker compose up` 之後、「上線了但沒資料」「畫面是空的」「幫我測一下」。
- **分類**：`quality/`
- **理由**：3/3 session 都手刻同一個 `for i in $(seq 1 25); do docker inspect ...` 輪詢與 401/200 驗證序列。獨立性略弱（可能該是 `wsl-fleet-deploy` 的 sub-skill），但「上線後資料是空的」在 session 2 佔了幾十輪，分層驗證順序本身有固化價值。**建議先做成 `wsl-fleet-deploy` 的一節，觀察下次是否獨立出現再拆。**

#### 4. `forecast-backtest-audit`
- **用途**：需求預測模型「輸給 naive baseline」的分級排查 —— 先驗回測窗長度是否足夠（而非只跑 1 天）、再驗資料對齊（料號改名、前導零、期間切分），最後才討論重訓 / 換模型。
- **觸發**：「模型效果不好是不是要重訓」「為什麼 X 輸給 naive」「回測結果怪怪的」。
- **不觸發**：股票/投組研究（用 `investment-research`）。
- **分類**：`workflow/`
- **理由**：session 2 花了大量篇幅，且結論很反直覺 —— 使用者一開始問「是不是要再訓練」，實際上前兩層（回測只跑一天、資料不對）就解釋了全部現象。這個「先別急著重訓」的排查順序值得固化。單一 session 出現，故列 Moderate。

#### 5. `verdandi-registry-client`
- **用途**：對接 Verdandi / Tukey AutoML 的模型登錄與推論契約 —— `X-API-Key`、`/registry/models`、`/registry/versions/{id}/api-key`、`/projects/datasets/{id}/latest-run`、批次登錄多個模型、docker network 打通。
- **觸發**：把某個 app 接上 Verdandi/Tukey 模型登錄、「登錄模型」「拿 API key」「接 AutoML」。
- **分類**：`backend/`
- **理由**：session 2、3 都在動 Verdandi，且 session 2 靠 `curl openapi.json | python3 -c ...` 反覆逆推 schema —— 這代表契約沒被文件化。屬於 reference 型技能，價值在省掉逆推。但只服務一個內部系統，通用性有限。

#### 6. `queue-throughput-triage`
- **用途**：判讀「跑很慢」到底是機器差還是併發設定 —— 看 running/queued 分佈、celery `--concurrency`、逐 task 耗時，並回答「該不該重跑」。
- **觸發**：「為什麼這麼慢」「全部在排隊」「我該重新跑嗎」。
- **分類**：`quality/`
- **理由**：session 3 的核心問題，推理鏈清楚（`concurrency=1` vs 本機 `2` → 總時間約兩倍，不是硬體差）。但只出現一次、範圍偏窄。
