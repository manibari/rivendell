# Dataflow Audit

確認一條資料流真的照宣稱在跑，而不是「看起來對」。

## 為什麼要有這個流程

驗收別人（或 AI）寫的程式碼時，最常見的失敗不是「功能沒做」，而是**畫面出得來、
資料其實沒走該走的路**：

- 說好 DB 是 system of record，實作卻是「先寫檔案、再側掛灌 DB」，DB 掛掉照樣出貨
- 表建好了、ingest 也有寫，但**沒有一個讀取端從那裡讀**
- 有個 `USE_NEW_PATH` 旗標，新路徑寫得很漂亮，**預設是關的**
- 失敗被 `except Exception: log.warning()` 吞掉，流程斷了三個月沒人知道

這些用讀碼看不出來，因為讀碼只告訴你「哪些路徑存在」。**要知道真的走哪條，
最快的方法是把東西弄壞，看誰還活著。**

所以順序是刻意的：**先畫地圖（便宜）→ 立刻反證（最值錢、最常被跳過）→ 才釘測試（貴）**。
反過來做的話，你會花很多力氣替假的邊寫測試。

## Phase 0 — 定範圍與「宣稱」

沒有宣稱就沒有對帳對象。開始前先落地兩件事：

1. **範圍**：一條具體的流程，有明確入口與出口。
   好：「上傳 .tgz → 解析 → 板圖點選看到原始欄位」。
   壞：「整個系統的資料流」—— 太大就切，一次一條。
2. **宣稱的流程從哪來**：ADR、`architecture.md`、決策紀錄、memory、
   PR 描述、或使用者口述。找到就 Read 全文，**不要只看標題或代碼引用**。

找不到任何書面宣稱時，別自己編一個。請使用者用一句話講「這條流程應該長怎樣」，
把那句話寫進報告當 target —— **有一個可以被打臉的宣稱，比一張沒有對照的圖有用得多。**

**成功狀態要定義成「看得到證據」，不是「看得到畫面」。**
例：「點一個元件，看到它在 PG 裡的原始欄位」比「板圖畫得出來」強，
因為前者證明資料真的在庫裡，後者只證明有人畫得出圖。

## Phase 1 — 靜態地圖（actual vs target）

目標：一張 **actual** 圖 + 一張落差表，每條落差附 `file:line`。

冷啟動（第一次進別人的 repo）：

```bash
bash <skill-dir>/scripts/seam-scan.sh [repo-path]
```

這支腳本只列位置、不下結論。它會掃四類接縫：寫入者／讀取者、被吞掉的失敗、
旗標與其預設值、handler 直接讀檔。把輸出當**待查清單**，逐條 Read 確認，別直接抄進報告。

接著逐項確認（每項都要能指到行號）：

| 要查的 | 具體做法 | 揪出什麼 |
|---|---|---|
| **入口** | 從 route / CLI / job 進入點往下追 | 真正的起點，不是 README 說的起點 |
| **每個 store 的寫入者** | 誰 write／INSERT／產檔 | 有沒有多個寫入者（雙頭寫 = 遲早分歧）|
| **每個 store 的讀取者** | 誰 read／SELECT | **寫了沒人讀的 store = 側掛，不是 SoR** |
| **繞道** | handler／前端有沒有跳過中間層直接讀來源 | 「35 處 router 直接讀 `work/`」這種 |
| **Schema ↔ 程式碼** | 欄位有寫沒人讀／有讀沒人寫 | 死欄位、空欄位 |
| **契約** | 前端呼叫的端點是否都存在、型別對不對 | 靜默 404、型別漂移 |

### 先做模組層對帳，再往下鑽儲存層

資料流不是一條直線，是**有分支、有迴圈、有旁掛工具**的東西。把它畫成直線就會漏掉
「品質有問題退回修正」「模型不滿意退回重建」「監控偵測衰退觸發重訓」這些真正決定
資料怎麼流動的邊 —— 而且產品的擁有者一眼就看得出來。

所以 Phase 0 找宣稱時，**要找到 flow / user-journey 那份文件**（`docs/flows/`、
`docs/requirements/`），不要只讀 README 與 architecture。分支與迴圈只寫在那裡。
那份文件常常還自標了每個模組是 HAVE 還是 NEED —— 那就是現成的對帳清單。

然後逐一比對三欄，一個模組一列：

| 文件怎麼說 | API 有沒有 | UI 接了沒 |
|---|---|---|
| HAVE / NEED / 根本沒列 | `grep '^@router\.' routers/*.py` | 在前端 grep 那個路徑字串 |

四種結果各有各的意思：

- **文件 NEED、但 API+UI 都有** → 文件過期。在 AI 加速開發的專案裡這是最常見的落差方向，
  而且傷害不小：照文件估工、排 roadmap、交接的人全都會判斷錯。
- **API 有、UI 沒接** → 寫了沒人讀的另一種形態，要問是留給外部服務呼叫還是忘了接
- **API 回 501 / NotImplemented** → 誠實的 seam，記下來但不算 bug
- **文件根本沒列** → 文件缺漏，通常是後來長出來的功能

**證據粒度是 `file:line`。** 寫「PG 在下游」沒有用，寫
「`ir_ingest` 先讀 `pcb-enriched.json` 才寫 PG — `backend/app/ir_ingest.py:270,406-416`」
才能被第三個人複查、也才逼自己真的去讀那一段。

畫圖時：**分開畫 actual 與 target 兩張**，不要在同一張上用虛線暗示。
兩張並排時落差自己會跳出來。圖的規格與自我截圖驗證見
[references/diagram-spec.md](references/diagram-spec.md)。

## Phase 2 — 反證（把東西弄壞）

**這段是整個 skill 的核心，也是最容易被跳過的一段。** 地圖上的每一條邊都只是假說；
反證是唯一能把假說變成事實的手段。

七個檢查項在問**兩件不同的事**，分開做：

| | 在問什麼 | 項目 |
|---|---|---|
| **甲組** | 資料實際走哪條路 | 1 拔依賴 · 2 旗標預設值 · 3 壞資料閘門 |
| **乙組** | 這個檢查擋不擋得住 | 4 治理欄位 · 5 閘門實測 · 6 基準會漂 · 7 失敗被吞掉 |

---

## Phase 2 · 甲組 —— 資料實際走哪條路

把東西弄壞，看誰還活著。操作細節見
[references/probe-recipes.md](references/probe-recipes.md)。

### 1. 拔依賴矩陣（兩個方向）

反證有兩種方向，第二種特別容易漏：

- **拔掉在用的** —— 證明地圖上的邊是真的
- **打開沒在用的** —— 把「有實作、但預設關著、零測試」的路徑**實際跑一次**。
  這種路徑的風險不是「它壞了」，而是「它哪天壞了不會有人知道」，
  而唯一能問出答案的方法就是跑它。跑完記得復原（刪掉 probe 資料、關掉臨時起的服務）。


對地圖上每個 store／服務，先**預測**「拔掉它，哪些出口會壞」，寫下來，**再真的拔**
（停服務、改壞連線字串、rename 檔案）跑一次主要旅程。

| 結果 | 意義 |
|---|---|
| 預測會壞、真的壞了 | 這條邊是真的 ✅ |
| **預測會壞、卻沒壞** | **這條邊是假的** —— 真實來源在別處，回頭找 |
| 預測不會壞、卻壞了 | 有隱性依賴，地圖漏畫 |

先寫預測再實驗，否則你會事後合理化任何結果。

### 2. 旗標預設值盤點

**預設值才是現況，另一半的程式碼是死的。** 每個旗標列一行：

```
名稱 | 程式碼預設 | env 實際值 | 預設走哪條路 | 另一條有沒有測試
```

程式碼預設與 `.env` 要**分兩欄記**：程式碼寫 `storage_backend = "minio"`、`.env` 覆蓋成 `local`，
表示那個預設值從來沒生效過 —— 只記其中一欄會得到相反的結論。

也要看**組合**，不只單一旗標。`AUTOML_BACKGROUND=true` 配 `CELERY_EAGER=false`，
在 `if eager and background` 底下是無效組合：env 讀起來像走背景執行緒，實際走的是別條路。

### 3. 壞資料閘門

餵空檔、半截檔、版本不認得的輸入，看系統是**明說不支援**還是**盡力而為**。

盡力而為在資料流裡幾乎都是錯的：**半套資料看起來像完整資料，是最惡劣的失敗**
（半張板子畫出來跟整張板子長得一樣，沒人會發現）。閘門應該擋在畫面之前，
而不是讓下游自己猜。

## Phase 2 · 乙組 —— 這個檢查擋不擋得住

甲組問完會得到一張「資料確實走這條路」的地圖。乙組問的是另一件事：
**路上那些看起來會攔人的關卡，真的攔得住嗎。**

這四項是這個 skill 最獨特的部分，也最容易被誤判成「已經做完了」——
因為它們**全都不會報錯**：測試綠燈、log 乾淨、畫面正常、文件看起來也對。

| # | 檢查 | 一句話怎麼判斷 |
|---|---|---|
| 4 | **治理欄位有沒有牙齒** | 這個欄位的用途若「定義／寫入／回傳顯示」三類就窮盡了 → 它只是標籤。真正的讀取端會**讓某個請求失敗** |
| 5 | **閘門實測** | 圖上畫成閘門／前置／必經的，就欠一次實測。問的不是「有沒有擋」，是**「從哪裡繞過去」** |
| 6 | **基準會不會漂** | 這個閾值是當初凍結下來的，還是每次拿當下資料現算的？**現算的不是基準，是描述** —— 它永遠不會報警 |
| 7 | **失敗被吞掉** | 這裡失敗時，使用者看得到嗎？看不到就是「流程看起來對、實際上斷了」的藏身處 |

四項的查法、判定表、關卡實況表格式、以及為什麼一定要放對照組，見
[references/no-teeth-checks.md](references/no-teeth-checks.md)。

**記錄時分三級，不要用真／假二分**：🟢 有讀取端會擋 · 🟡 只約束同類資料不影響對外 · 🔴 只有寫入與顯示。

## Phase 3 — 釘測試（只釘反證確認重要的接縫）

不要為地圖上每條邊寫測試。**只釘兩種**：反證證明是真的、而且壞掉會沒人發現的邊。
四種形狀夠用了：

| 形狀 | 守什麼 | 什麼時候用 |
|---|---|---|
| **Tracer bullet** | 一筆真資料端到端，每站 assert 它真的在 | 主幹流程，第一個要有的 |
| **雙路徑 parity** | 兩個來源的同一欄位逐欄相同 | 遷移／切換期間，抓漂移特別靈 |
| **外部真值 baseline** | 對第三方工具或人工真值逐筆零差異 | 有權威答案可比時（別自己跟自己對）|
| **筆數守恆** | 入口 N 筆，每站還剩幾筆 | 漏單、去重過頭、靜默截斷 |

**測試 skip 掉等於沒測。** fixture 缺、DB 沒起、外部服務不在，就讓它**紅**，
不要 skip 成綠燈 —— 「跳過了還報綠」正是這個 skill 要防的那種失敗，
不要把它蓋進自己的測試套件裡。

## Phase 4 — 產出

交付清單，缺一會被退：

- [ ] **功能關係圖** `dataflow-functions-<YYYY-MM>` —— **主表**，先做這張
- [ ] `INDEX.md` —— 說明怎麼看、怎麼維護（範本：[assets/index-template.md](assets/index-template.md)）
- [ ] 落差報告（.md）
- [ ] 儲存層 `dataflow-stores-actual-<YYYY-MM>`（＋有書面宣稱時加 `-target`）
- [ ] 模組清單表（進報告即可，不一定要畫成圖）
- [ ] 全部 PNG **內嵌進報告**

### 產出要用中心輻射的結構

一次稽核會生出七八個檔案，散著放等於沒交。**功能關係圖是主表，其他都是它某一格點進去的細節**，
檔名用 `node-<帶>-<節點>` 讓人一眼看出掛在哪裡，並寫一份 `INDEX.md` 講明白這件事。

主表交出去之後還會被繼續用 —— **開發新功能時先改主表**（加一格、接線、標狀態）再寫程式。
命名規約、四種狀態顏色、維護規則、以及「顏色過期比沒有顏色更糟」的理由，見
[references/doc-structure.md](references/doc-structure.md)。

**先畫功能關係圖。** 實測下來，其他形式的圖都會被退：模組全景會被說「只看到各種方框」，
實體流轉圖會被說「看不出各個 function 之間的關係」。使用者要的是**誰是誰的前置、
交出去的是什麼、哪裡會退回** —— 只有這張回答得了。

版面直接抄 [assets/function-map-template.html](assets/function-map-template.html)：
1600–1900 寬的手工正交排版，band 分列、節點等高、邊上帶白底標籤片、回頭路走外側。
不要用自動排版重推一次（理由見 [references/diagram-spec.md](references/diagram-spec.md)）。

圖最容易被跳過：落差表寫完會很像已經交代完了，但表格是給查證的人看的，
圖才是給決策的人看的。

主產出是**落差報告**（圖是附件，但附件不能不交）。用
[assets/gap-report-template.md](assets/gap-report-template.md)，結構固定：

```
# <範圍> 資料流稽核（YYYY-MM-DD）
**結論先講**：一句話講最重要的落差
## 宣稱的流程        ← 來源＋日期
## 實際的流程        ← 落差表，每列附 file:line
## 反證結果          ← 拔依賴矩陣／旗標盤點／被吞掉的失敗
## 建議釘住的接縫    ← 哪幾條要測、用哪種形狀
## 不要動壞的東西    ← 現有守得好的地方，交接時最容易被誤刪
## 接手要先決定的事  ← 產品／架構決策，不要替使用者決定
```

放進**目標 repo 既有的文件慣例**（`docs/architecture/`、`docs/verification/`、`docs/adr/`
都常見）—— 先 `ls docs/` 再決定，不要硬套一個新目錄進別人的 repo。

落差表旁邊一定要有一節**「好消息 / 這幾件事做對了」**。稽核報告只寫壞的，
接手的人會以為要全部重來，然後把還在守著的東西一起砍掉。

「不要動壞的東西」那節常被漏掉，但它是報告裡最保護人的一節：
稽核報告會被當成「這裡全爛了」的授權，接手的人一刀砍掉還在守著的測試或
刻意獨立的離線路徑。明寫出來。

## 收尾 checklist（線 4，不進主流程）

主流程跑完後掃一遍，有中的補進報告：

- [ ] 每階段的前後不變量寫下來了嗎（`status = ready` 才給資料、版本不認得就擋）
- [ ] 失敗後資料留在哪？狀態機有沒有孤兒狀態（永遠卡在 `processing`）
- [ ] 同一輸入跑兩次會不會多出重複列（冪等）
- [ ] 多表寫入有沒有包在同一個 transaction
- [ ] 產出了但沒人讀的檔案／表（孤兒產物）
- [ ] ADR／決策紀錄與現況的 drift，有沒有回頭更新文件

## 常見的自我欺騙

- **「有測試」不等於「守在對的地方」** —— 先看測試釘的是哪條接縫，再看它跑不跑得起來
- **「表裡有資料」不等於「有人從那裡讀」** —— 寫入者與讀取者要分開查
- **「代碼有提到」不等於「我讀過內容」** —— 看到 ADR 編號、WBS code 就以為知道內容，
  是最常見的憑空腦補來源。grep + Read 全文再引用
- **「跑得起來」不等於「走了預期的路」** —— 沒拔過依賴，就還不知道
