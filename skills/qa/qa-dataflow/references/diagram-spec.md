# 資料流圖規格（Phase 1 附件）

圖是報告的附件，不是主角。**先有落差表，再畫圖** —— 沒有落差表的圖只是好看的猜測。

## 兩張圖，不是一張

`dataflow-actual-<YYYY-MM>` 與 `dataflow-target-<YYYY-MM>` 分開出。

不要在同一張上用虛線／灰底暗示「這條還沒做」—— 讀的人會自動把它讀成「快好了」。
兩張並排時，落差自己會跳出來，不需要標註。

target 圖只在有書面宣稱時才畫。沒有宣稱就只出 actual，並在報告裡寫明「無書面 target」。

## 三種問題，三張圖，不要想用一張講完

被退稿最多次的原因，是想用一張圖同時回答三個不同的問題。它們的節點根本不同：

| 讀者的問題 | 圖 | 節點 | 邊 |
|---|---|---|---|
| 有哪些模組？哪個沒做？ | 模組全景 | 功能模組 | 沒有邊（這是清單，別假裝有流程）|
| 誰是誰的前置？交出去什麼？ | **功能關係圖** | 功能 | 傳遞的識別碼（`dataset_id` → `split_id` → `run_id` → `version_id`）|
| 資料本身怎麼流？躺在哪？ | 資料流（實體） | 資料實體 | 產生下一個實體的動作 |

「看不出各個 function 之間的關係」＝ 缺第二張。**功能關係圖的價值全在邊的標籤上** ——
邊上寫「傳什麼」才叫關係，只有箭頭等於沒說。前置關係從程式碼的參數依賴讀出來：
一個端點要 `split_id` 才能呼叫，就代表切分是它的硬前置，不用猜。

同時標上**哪些是回頭路**（退回修正、重訓、不滿意重做）與**哪些是旁掛**
（唯讀分析、吃已註冊模型的工具）。少了回頭路，圖會看起來像單向管線，
而真實系統幾乎都是循環。

### 主表最後一帶放「關卡實況」

主表畫完會有一堆看起來像閘門的格子。**把「它到底擋不擋得住」做成主表的最後一帶**，
四欄：關卡 / 圖上看起來 / 實際 / 怎麼被跨過去（做法見 SKILL.md Phase 2 第 5 項）。

放在主表上而不是只放報告裡，是因為它的讀者不是稽核的人，是**下一個要動這條流程的人**：
要在某一關加東西，第一件事就是看那關現在擋不擋得住。帶的副標直接寫出這個用途。

一定要留一列**真的有擋**的當對照組，否則整張表讀起來像在數落。

### 每個帶都要有出邊，終點落在「人做了什麼」

一個帶如果只有進沒有出，讀起來就是「這一端什麼都不產出」。實際踩過：把產品回答
「該怎麼設定」的那一整帶畫成三個不相干的旁掛工具、一條出邊都沒有 —— 圖等於在說
這裡是死路，而它其實是整個產品的交付點。

補法是把終點畫出來，而且**終點要是人或對外的產出**，不是又一個內部元件：
「設定建議 → 人拿去調機台」。畫得出這條邊，才證明你知道這個帶是為了什麼存在。

### 帶的入口要標「帶進來的是什麼」，還要標「不是什麼」

負向資訊常常比正向的更能防止誤解：

> 帶進來的只有模型檔＋訓練時記下的中繼資料（編碼規則 · 因子範圍 · 資料涵蓋範圍）
> —— **原始資料不隨行**

沒有後半句，讀圖的人會理所當然以為下游拿得到原始資料，然後基於這個誤解去規劃功能。

**多入口一定要全部列出來，並標明哪個會繞過關卡。** 一格看起來只有一個入口，
實際上有四個入口的情況很常見；繞過關卡的往往就是後來補的那個捷徑
（例：「③ 一鍵多響應建模會自己註冊，使用者不會經過模型登錄頁」）。

### 同一件事的兩套實作，框在一起並把決策標上去

同一個問題有兩個入口／兩套演算法時，不要畫成兩格平行的功能 —— 讀的人不知道該用哪個。
框成一格「同一件事的兩套實作」，副標寫上決策狀態（已決定合併／待評估），
框內各自標防護狀態，用三態而不是二態：

`✓ 有防護` · `✗ 無防護（附實測到的異常值）` · `◐ 只做一半 / 方向要調整`

`◐` 那一態最有用 —— 「只擋一半」是最容易被抽查漏掉的狀態。

### 節點名用使用者看得到的名字

主表是給人看的，不是元件清單。`Prediction Profiler` 要寫成「最佳化模擬器」、
`PSO solver` 要寫成「參數追尋」—— 內部元件名放在副標。判準：**這個名字在產品的畫面上
出現過嗎**？沒有的話，讀圖的人得先翻譯一次才看得懂自己的產品。

帶的標題也一樣，要寫「這個帶做完會得到什麼」而不是分類名：

- 「應用 —— 拿『已註冊』的模型回答『該怎麼設定』」 ✅
- 「旁掛工具」 ❌（分類名，看不出它跟主幹的關係）

### 排版：多 band 的關係圖不要交給自動排版

mermaid 的 `flowchart` 在單一鏈路很好用，但一旦有 3-4 個 band 加上跨 band 的回頭邊，
dagre 會把它排成長條或階梯狀，邊互相穿越、subgraph 標題被線壓住 —— 實測 LR 排出
2584×559 的長條，TB 排成對角階梯，兩種都不能看。

節點超過 ~15 個又要分 band 時，改成**手工正交排版**：一個 band 一列、
同列的節點等高、跨 band 的邊走列與列之間的水平通道、回頭路走外側。
邊的標籤加**白底標籤片**（`rect` + 置中文字）壓在線上，否則短間距的標籤一定會疊到方框。

## 節點是資料實體，不是功能模組

**資料流圖最容易畫壞的方式，是把功能模組當節點。** 一排「建立專案 / 資料匯入 / 訓練 /
模型註冊」的方框，看起來很完整，但它是**清單**不是**流程** —— 沒有東西在流動，
讀的人第一句話會是「我看不出資料的流程，只看到各種方框」。

節點要換成**資料實體**：從程式碼的資料模型（`models.py` 的 table、ORM class、
主要 dataclass）挑出「會被存下來、有生命週期、下一步會拿它當輸入」的東西：

```
Dataset → Split → Run(+artifact) → ModelVersion(+registry 副本) → 推論紀錄
```

然後：

- **箭頭是產生下一個實體的動作**（切分 / 訓練 / 註冊 / 上線），標在連接線上，不是節點裡
- **每個實體標它躺在哪**：PG 哪張表、物件儲存哪個 key、有沒有經過佇列 —— 這是資料流圖
  跟功能圖最大的差別，也是稽核落差會現形的地方
- **回頭箭頭一定要畫**：退回修正、不滿意重做、偵測衰退重訓。少了它就變成單向管線，
  而真實系統幾乎都是循環
- **唯讀的東西用虛線掛在旁邊**：分析、報表、探索工具讀資料但不產生新實體，
  混進主幹會讓人以為資料流經過它們

功能清單與資料流是**兩張圖**，不要合併：一張回答「有哪些模組、哪個沒做」，
一張回答「資料怎麼流」。在報告裡明講兩張的分工，否則讀的人會以為其中一張是另一張的簡化版。

## 畫完整功能骨幹，把稽核判讀疊上去

**最容易犯的錯：把圖裁成只剩你查的那一段。** 稽核範圍是「儲存與派工」，
就只畫「上傳 → 存檔 → 訓練」，結果圖看起來像這個產品只有存檔和派工 ——
擁有這個產品的人第一眼就會說「怪怪的，我明明還有建專案、模型註冊、生命週期管理」。

正確做法（也對映 `~/.claude/CLAUDE.md`「保留物理架構，疊加 overlay」那條）：

1. **先攤功能骨幹**：`ls routers/`、`find app -name page.tsx`、讀 models.py 的實體，
   把使用者看得到的步驟依序排出來 —— 不要憑常識猜這個產品「應該有什麼」。
2. **底下加一條 store rail**：每個 store 一張卡，寫清楚**哪幾步寫它、哪幾步讀它**。
   資料流的重點在這一層，功能骨幹是它的座標系。
3. **橫向機制單獨一條帶**：身分權限、稽核記錄、營運基線這種貫穿全流程的東西，
   給一條帶，不要塞成流程裡的一個節點。
4. **判讀 overlay 放最後一排**：✗ / ✅ 各配一句為什麼。

在報告裡寫明「**圖是完整骨幹，稽核深度只在某一層**」，否則讀的人會以為你逐項驗過全部。

## 版面

沿用 `~/.claude/CLAUDE.md` 的 Diagram & Slide Output Defaults：

- **16:9 固定 1600×900**，`overflow: hidden`。塞不下就拆多張，不要改成 portrait
- 字級：h1 32-36px、區塊大標 18-22px、卡片 title 16-20px、footer 10-12px。
  任何 <12px 的元素要說得出理由
- 不同性質的東西用**不同的盒 + 不同色系**（來源 / 解析 / 產出 / 消費端），
  不要共用邊框只在中間斷開
- **箭頭一定要有**。沒有箭頭、沒有元件互動關係的不是資料流圖，是工作包列表
- footer 標來源與日期（`依 YYYY-MM-DD 程式碼實查`）—— 逼自己回頭驗證，
  也讓半年後的讀者知道這張圖過期了沒

## 在 actual 圖上標判讀

actual 圖的價值在於它**帶結論**，不是單純描述。用三個符號在圖上直接說話：

```
✗ ODB++ 不是直接進 PostgreSQL —— 先 parse 成 pcb.json，PG 在倒數第三步才灌，且非致命
△ 規則層方向對，但兩個細節要修
✅ pack 刻意獨立於 PG 產生（離線路徑的地基）
```

每個符號後面接一句「為什麼」，不要只放符號。

## 產生方式

擇一，不要三種都做：

| 工具 | 什麼時候用 |
|---|---|
| 手寫 HTML（16:9 版面）| 要標判讀、要密集排版時最好控制 —— PTI-ARES 用這個 |
| `excalidraw-diagram` skill | 給非工程讀者、要手繪感時 |
| `mermaid-diagram` skill | 純結構、要自動排版、之後要進 git diff 時 |
