# 它擋得住嗎 —— 四種「有做但沒作用」的查法

Phase 2 後半四項的操作細節。共同點：**這些失敗全都不會報錯** ——
測試綠燈、log 乾淨、畫面正常，只有主動去問才問得出來。

判準速查（主檔留的就是這四句）：

| 檢查 | 一句話怎麼判斷 |
|---|---|
| 治理欄位有沒有牙齒 | 這個欄位的用途若「定義／寫入／回傳顯示」三類就窮盡了 → 純標籤 |
| 閘門實測 | 圖上畫成閘門就欠一次實測；問的不是有沒有擋，是**從哪繞過去** |
| 基準會不會漂 | 這個閾值是當初凍結的，還是每次現算的？現算的不是基準，是描述 |
| 失敗被吞掉 | 這裡失敗時，使用者看得到嗎？ |

---

## 治理欄位有沒有牙齒

狀態欄位（`status` / `state` / `environment` / `enabled` / `role` / `tier`）是「看起來做完了」
的重災區。一個治理欄位要真的產生約束，需要六件事：

**欄位 · 寫入 API · 轉移規則 · UI · 稽核 log · 有人讀它並據此拒絕請求**

前五件齊全就會讓所有人（包括當初寫的人）認定做完了。**第六件才是它存在的理由**，
而它缺席時不會有任何錯誤訊息 —— 沒有 log、沒有告警、測試也是綠的。

查法很機械，一個欄位一次：

```bash
rg -n '\bthe_field\b' --glob '!*test*'
```

把每一處分成三類：**定義**、**寫入**、**放進 API 回應／畫面**。
如果三類就窮盡了，它就是純標籤。真正的讀取端長這樣 —— 出現在條件式或查詢條件裡，
而且**會讓某個請求失敗或看不到東西**：

```python
if v.lifecycle_state == "retired": raise HTTPException(403, ...)   # 有牙齒
select(ApiKey).where(ApiKey.revoked.is_(False))                    # 有牙齒
return VersionOut(environment=v.environment, ...)                  # 沒有 —— 只是回傳
n_prod = sum(1 for v in vs if v.state == "production")             # 沒有 —— 只是統計
```

分三級記錄，不要用真/假二分：

| 級別 | 意思 |
|---|---|
| 🟢 有牙齒 | 有讀取端，會擋掉請求 |
| 🟡 只咬自己 | 有狀態機／不變量，但只約束同類資料（例如「同時只能有一個 production」），不影響對外行為 |
| 🔴 純標籤 | 只有寫入與顯示 |

**報告裡一定要放對照組**：把同一個系統裡真的有牙齒的欄位（權限、API key 撤銷）
跟沒牙齒的排在同一張表。有對照組，「沒牙齒」才會被讀成客觀觀察，
而不是稽核的人在挑剔；也才看得出這是能力問題還是**當初就沒打算擋**。

順帶查兩個常見的相鄰誤解：

- **「自動記錄」是不是真的自動** —— 呼叫端要自己回填的日誌，跟系統自己寫的日誌，
  在圖上長得一模一樣。查寫入者是誰：是 handler 自己寫，還是有個 `POST /logs` 等人來餵。
- **指標函式不等於資料庫** —— `record_xxx()` 常常是 Prometheus 計數器，不落 DB。
  名字很像「記一筆」，但重開就沒了。

### 5. 圖上畫成閘門的，實測它擋不擋得住

**只要你在圖上把某一格畫成「閘門」「前置」「必經」，就欠一次實測。**
稽核報告寫「品質報告是全流程的閘門」很順口，但實際跑一次會發現它只在畫面上顯示紅字，
有 blocker 照樣訓練得下去 —— 圖因此在騙人，而且是你自己畫的。

一格一列，做成**關卡實況表**（四欄，缺一不可）：

| 關卡 | 圖上看起來 | 實際 | 怎麼被跨過去 |
|---|---|---|---|
| 品質報告 | 全流程的閘門 | 純標籤 | 有 blocker 照樣能訓練，只在畫面顯示紅色標籤 |
| 切分 | 必要前置 | **只擋一半** | forecast 自動合成時序切分、分群自動合成隨機切分，都不會問你 |
| 註冊 | 人工決定 | **自動跨過** | 一鍵多響應建模訓練完會自己註冊 |
| 服務金鑰 | 預設停用 | **真的有擋** | 查詢條件直接濾掉已撤銷的金鑰 —— 對照組 |

第四欄「怎麼被跨過去」是重點：**不是「有沒有擋」的是非題，是「從哪裡繞過去」的問答題**。
最常見的三種繞法：另一個端點走舊路、自動流程代替人工決定、只在 UI 擋而 API 沒擋。

「只擋一半」會比「完全不擋」更危險 —— 它會讓抽查的人剛好抽到有擋的那條，然後結案。

這張表要放進**主表本身**（見 Phase 4），不是只放在報告裡。它會被反覆查閱：
規劃新功能時要在某一關加東西，第一件事就是看那關現在到底擋不擋得住。

**在拿來規劃的圖上，「畫成閘門但其實不擋」是成本最高的一種錯誤** —— 它不只是記錯，是讓後面每一個照著它做決定的人都跟著錯。

### 6. 會自己跟著資料調整的基準，永遠不會報警

跟「沒有牙齒」同一家族，但更難看出來：**讀取端存在、也真的會比對，只是它比對的基準
是拿當下這批資料現算的。** 基準跟著漂，門檻就永遠追得上現況，警報一次都不會響。

典型長相：

- 管制圖每次都用傳進去的資料重算上下限 → 製程慢慢漂移會被吸收進界限，圖永遠正常
- 異常偵測用當批資料的分位數當閾值 → 整批都異常時，它會說整批都正常
- 「跟基準比」的監控，基準取的是最近 N 筆而不是訓練時凍結的那份

判準一句話：**這個閾值是當初凍結下來的，還是每次現算的？** 現算的就不是基準，是描述。

同一種缺陷還有一個鏡像：**在資料涵蓋範圍外照樣自信作答**（最佳化器把因子推到訓練資料
從沒出現過的區間，回一個很漂亮的數字）。兩者都是「系統不知道自己不知道」，
查法一樣 —— 找出那個界限是哪裡來的，然後餵一筆明顯超出範圍的輸入看它有沒有吭聲。

## 被吞掉的失敗

grep `except Exception` 後接 `pass`／`warning`、空 `catch {}`、
`non-fatal`／`best effort` 註解、`unwrap_or_default()`。每一處問一句：
**這裡失敗時，使用者看得到嗎？** 看不到的話，這就是「流程看起來對、實際上斷了」的藏身處。

特別標出**非致命的寫入**：某個 store 寫失敗不擋出貨，等於它從來就不是 SoR，
不管文件怎麼寫。
