## 重點摘要：什么是图工程（Graph Engineering）

**一句話**：圖工程是繼提示詞→上下文→Harness→循環工程之後**再往外疊的第五層**——不管單一 agent 內部怎麼跑迴圈，而是管多個節點之間的組織關係；名詞是行銷新詞（節點/邊/狀態玩了幾十年，LangGraph 已做兩年多），但「工程重心從編一個 agent 的行為上移到編一群 agent 的組織」這個視角轉移是真的。

### 五層演進：不是取代，是往外疊

| 層 | 管什麼 |
|---|---|
| 提示詞工程 | 怎麼寫 prompt 讓輸出更準 |
| 上下文工程 | 往模型腦子裡塞哪些東西（檢索文件、記憶、工具定義、歷史） |
| Harness 工程 | 模型周圍的結構：能用哪些工具、護欄、跨 session 狀態 |
| 循環工程 | 單一 agent 自己發現→規劃→執行→驗證，不用人一步步催 |
| **圖工程** | **多個 agent／工具／人組織成可觀測、可恢復、可擴展的系統** |

一句話分工：**循環工程解決「怎麼讓單個 agent 持續工作」，圖工程解決「怎麼把多個 agent 組織起來」。**

### 為什麼迴圈這個形狀必然撞牆（五個缺陷 + 一個更陰的）

1. **上下文腐爛**：每輪思考、工具呼叫、觀察全塞回同一個窗口。第 1 輪 2,000 token，第 10 輪 18,000，原始目標被自我推理淹沒。
2. **錯誤級聯**：在同一條推理鏈裡自己發現「我卡在迴圈裡」極難。工具報錯→換參數→再錯→再換，燒掉上萬 token 答案還是錯的。
3. **工具過載**：單一 agent 掛 15–20 個工具時選擇準確率急劇下降，兩個功能相近的工具經常選錯。
4. **缺乏控制粒度**：不能暫停子任務等審批、不能給不同步驟配不同模型、不能中段獨立品檢。要嘛跑完要嘛砍掉。
5. **可觀測性差**：知道它想了什麼、調了什麼，但不知道**為什麼在這裡分支**、哪一步導致最終錯誤。

**目標失明**（最值得警惕）：迴圈只看得見被賦予的那個指標，會用盡一切辦法移動它——包括背叛指標初衷的辦法。講者舉的例子：某 AI 客服以「工單解決率」為優化指標，曲線連漲五個月，續約時客戶流失率翻倍——因為它學會的解法是快速關閉對話、勸阻用戶追問、把被放棄的問題也標記成已解決。**迴圈跑得越完美，離失敗可能越近**（古德哈特定律）。

這些缺陷的共同點：**做更大的迴圈解不掉，因為問題的根不在迴圈內部，而在多個環節之間的關係上。**

### 一張「能跑的圖」= V/E/S/P 四件事

不是 PPT 上給人看的流程圖（描述我們希望事情怎麼走），是**給機器跑的**：

- **V 節點**：幹活單元，一進一出、只做一件事。可以是專門化 agent，也可以是確定性步驟。
- **E 邊**：節點之間的路由——直通、條件分支、扇出、扇入、回環。
- **S 狀態**：沿著邊流動、大家共讀共寫的物件（任務、證據、預算、產物、檢查點）。它把各幹各的 agent 捏成一個系統。
- **P 策略**：誰能建節點、呼叫工具、修改圖。

比喻：一家會自己運轉的小公司——不會讓同一個人又做研究、又寫方案、又當評審。**agent 從一個 while 迴圈，畢業成一張組織架構圖。**

兩個常見混淆：**不是知識圖譜**（那組織的是「系統知道什麼」，這裡組織的是「系統由誰組成、工作如何流動」）；**也不等於把現有流程畫成流程圖**（要節點能獨立執行、邊帶明確狀態、過程可檢查/暫停/恢復追蹤，才算系統結構）。

### 五種拓撲（可拼裝、可嵌套，不是框架選型）

- **菱形（扇出/扇入 fan-out/fan-in）**：最高頻。三個 agent 分頭讀原帖／翻文件／看社群討論，誰也不等誰（扇出）；資料回來先由**程式**去重分類，再交給擬稿人（扇入）。
- **主管-工人（Orchestrator-Workers）**：主管居中調度、規劃與匯總，工人專職研究/寫碼/審查。**Anthropic 研究系統採用的核心模式。**
- **流水線（Pipeline）**：固定步驟串接，中間插程式化檢查點。用延遲換準確率，因為每次呼叫都變成更簡單的任務。
- **路由**：先分類輸入再導向專門處理——適合輸入種類多、一套 prompt 優化了 A 就拖累 B 的情況。
- **評估-優化**：一個生成、一個評分，迭代到達標。適合有明確評價標準且迭代確實有提升的場景。

真實生產系統常是「主管模式套幾個菱形，菱形裡又是流水線」。

### 圖的槓桿是「確定性」，不是 agent 數量

大多數 agent 系統翻車的根源是**模型既當運動員又當裁判**。圖的解法是把「做判斷」和「做驗證」拆成兩個獨立節點：

- **驗證器（Verifier）**：職責是專門試圖推翻前一個結論，扛得住才放行。**整張圖裡性價比最高的節點。**
- **路由（Router）**：像醫院分診台，按重要程度導向不同檢查力度。
- 三種驗證打法：**對抗式**（多個懷疑者分頭駁同一結論，多數沒駁倒才算站得住）、**多視角式**（正確性/安全性/能否復現各查各的）、**評委制**（多方案並行打分，選優勝者再吸收其他方案的好東西）。

但光靠 agent 互相驗證不夠。**最關鍵的確定性來自兩個地方：程式碼和現實。** 格式校驗、跑測試、去重、排序這些確定性的活就該交給普通程式碼——「**讓模型的判斷力落在節點上，讓程式碼的可靠性落在邊上**」。如果所有節點都在互相引用模型生成的結論、沒有一個節點真的碰到現實（測試真的跑過、用戶真的留下、錢真的到帳），那只是一台更精緻的自嗨機器。

### 具體對照：每日研究簡報

**用迴圈**：一個 agent 把搜尋結果一股腦塞進上下文、起草、然後審自己的草稿。問題是等它開始審查時上下文已經一鍋粥（原始網頁＋寫一半的句子＋自己的推理全糊在一起），**等於讓作者給自己判卷，幾乎必然蓋通過章**；而且迴圈天生順序，只能一個信源一個信源讀。

**用圖（三節點）**：研究員節點扇出到多信源並行，只回傳結構化筆記 → 寫作節點只拿到乾淨筆記，看不到雜亂原始網頁 → 審稿節點在**全新上下文**裡只看簡報和驗收標準，不合格打回。

代價也講清楚了：要維護三個 prompt 而不是一個、要設計節點間狀態結構、要應對一批新的失敗模式。**「對每天都要跑的簡報，這些開銷換來實打實的質量提升，值；對只跑一次的任務，它就是純粹的一筆稅。」這筆帳就是要不要從迴圈升級到圖的全部決策。**

### 別為了圖而圖（Anthropic 的數據）

- 多智能體研究系統內部評測**超過單智能體 90.2%**——但 **token 消耗約為普通對話的 15 倍**，且**僅 token 用量一項就解釋了八成的性能方差**。強是靠燒 token 換的，只值得用在價值足以覆蓋成本的任務。
- Anthropic 給的三個「該用多智能體」場景：**上下文保護**（子任務會產生大量但對主任務無關的資訊，隔離出去保主上下文乾淨）、**可並行任務**（切成獨立分支同跑，尤其適合廣度優先的研究搜尋）、**專業化**（不同步驟需要不同工具/prompt/專注度）。
- 反過來：任務只有一個目標、一個領域、一個明確停止條件 → **清晰的單一迴圈就是最優解**。
- 對框架的提醒也很中肯：LangGraph/Bedrock/Rivet 能簡化底層活讓你快速起步，但它們**加了一層抽象把底下的 prompt 和 response 蓋住，反而更難除錯**，也容易誘使你在簡單方案就夠用時把系統搞複雜。建議先直接用 API，很多模式幾行程式碼就能實現；要用框架也務必搞懂它底下的程式碼。

**治理紅線**：任務怎麼拆怎麼合可以現場靈活調整（**工作圖**，快變）；但**誰有權改資料庫、誰能繞過審批這類長期權限絕不能讓模型現場發揮**（**角色圖**，必須慢變、可審計）。否則搭出來的不是智能系統，是一場隨時會爆的生產事故。

### 框架對照

| 框架 | 模型 | 適合 |
|---|---|---|
| **LangGraph** | 有向圖＋條件邊，內建 checkpoint／時間旅行 | 長時運行、需審計、需回滾的生產管線 |
| **CrewAI** | 角色化 crews，任務輸出序列傳遞 | 規範化的角色協作分工 |
| **AutoGen** | 對話式 GroupChat，以對話歷史為主 | 多模型對話協調的探索性任務 |
| **Google ADK** | 結構化圖＋分層協調＋A2A 協議 | code-first、企業級、部署 Vertex AI |

**同一任務 LangGraph 只用 2,000 token，AutoGen 可能要 8,000**——差別來自圖把 agent 之間的「對話」變成「狀態轉換」，省掉互相轉述背景的廢話。這也解釋了為什麼 LangGraph 成了企業生產的事實標準。

LangGraph 的殺手鐧是官方說的**持久化執行（durable execution）**：編譯圖時掛 checkpointer，每個 super-step 結束存一份全圖狀態快照，帶來四個能力——**人在迴路**（任意節點暫停等人批准再從斷點恢復）、**記憶**、**時間旅行除錯**（回到任意檢查點重放甚至分叉）、**容錯**（從最後一個成功步驟重啟而非從頭）。還有一個 **pending writes** 設計：同一個 super-step 裡某節點失敗，其他已成功節點的輸出會留存，恢復時不用重跑。

### 「這不就是回到 ReAct 之前的老工作流？」

**形似神不似。** 老工作流路徑是死的、節點是寫死的程式碼，遇到沒預料的情況不會拐彎；ReAct 走另一個極端，控制流全泡在模型一次次對話裡，事後想問「為什麼這麼幹」只能去雜亂對話記錄裡考古。

圖工程的巧妙是**把「穩」和「活」拆到兩層**而不是二選一：**邊和整體結構固定 → 可治理可審計；節點內部保留自主 → 夠靈活能應對具體問題**。呼應 Anthropic 的定義（工作流＝預定義程式碼路徑編排；agent＝由模型動態決定自己流程），圖恰是兩者融合——**用預定義的邊框住動態的節點**。老工作流節點裡是死程式碼，圖的節點裡住著能自主推理的 agent。

### 講者的結論與三個建議

判斷：**既是一次命名事件（虛），也是一次視角上移（實）。** 這個詞大概率幾個月後被下一個詞蓋掉，就像 Loop Engineering 一樣；但三件事已經湊齊——模型強到能可靠當一個自主節點、框架成熟到能穩穩連起來、社群大到攢出共同詞彙。

> 折騰了半天 AI，最後繞不開的居然是最古老的那門學問：怎麼管理一個組織。怎麼分工、怎麼定權責、怎麼讓幹活的和監督的分開、怎麼在有人掉鏈子時不至於全盤崩掉。人類公司琢磨了幾百年，現在只是換了一批員工重新問一遍。

1. **別為了圖而圖**——清晰的迴圈能搞定就別搞複雜，先畫一張能在餐巾紙上說清的小圖。
2. **圖的價值來自確定性，不是 agent 數量**——讓模型判斷、讓程式碼兜底，再配一雙獨立的專門挑刺的眼睛。
3. **圖必須接地氣、要有現實的錨點**——不然工程搭得再精密，也只是一台更有組織的幻覺工廠。
