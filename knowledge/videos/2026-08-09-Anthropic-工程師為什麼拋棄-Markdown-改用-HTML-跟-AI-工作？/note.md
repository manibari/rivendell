## 重點摘要：Anthropic 工程師為什麼拋棄 Markdown 改用 HTML 跟 AI 工作？

**一句話**：AI 把「產出」壓到趨近免費之後，瓶頸從「誰來做」變成「誰來看、誰來判斷」——所以真正的槓桿不是逼 AI 多生一點，而是**改變 AI 交回給你時的格式**：文字整理留給 Markdown，要「快速看懂狀態、比較方案、做決定」就換成一頁能開、能比、能拖的 HTML 工作頁。

> ⚠️ 標題比內容激進。講者明說「**我不會叫你用 HTML 全面取代 Markdown，也不是說哪個一定比較好**」——這是分工，不是替換。

### 起點：哈佛研究說 AI 讓人更累

Harvard Business Review 2026 年 2 月的研究，研究員花八個月追蹤一家 200 人的美國科技公司、做了 40 多場訪談。結果是 AI 不僅沒省事，反而工作量變多、步調變快，連原本不算工作時間的空檔也被塞滿——最後換來壓力堆積、認知疲勞、品質下滑、決策變差，直到 burnout 跟離職。

研究把影響拆成三塊：

1. **Task expansion（工作範圍變大）**：PM 開始寫 code、marketing 開始做設計。不是公司改了職責，是 AI 讓這些事**看起來變得可以嘗試**。
2. **工作／非工作邊界模糊**：「反正只是一句提示詞、反正它可以先跑、反正等一下回來看就好。」
3. **Multitasking 變多**：一邊做自己的事、一邊讓它產文件、一邊等 agent 跑完，又順手開另一個 session。每件事都在前進，但注意力一直在切換。

講者接的是《Four Thousand Weeks》裡的**現代版薛西弗斯**——他推的不是石頭，是清空 email inbox；剛靠上椅背深呼吸，提示音就響了。書裡那句話是全片的引擎：**「我們用來試圖掌控一切的科技，最後總是會失敗，因為它們會把那個『一切』本身變得更大。」**

### 真正的瓶頸：稀缺的不是產出，是理解

「過去稀缺的是誰來做，現在稀缺的是誰來看、誰來判斷、誰來確認下一步。」AI 推出來的每個東西都要有人重新讀、重新理解、重新判斷 → 決策疲勞。

**這種審核成本最麻煩的地方是它無法被量化**：你沒多開一場會、沒多交一份報表，可是腦子一直在切換、回想、比對、判斷。上級看不到這個成本，系統也不會記錄。表面上效率變高、事情推進更快，實際上自己累成狗。

而且 AI 的工作方式**會自然而然把你推向多工**（它在跑的時候你不想乾等），等你處理完第三件事回到第一件事，得重新回憶：哪些決定做過、哪些還沒過、哪些風險沒看、**哪一段是 AI 自己亂補的**。

### 為什麼「產出」不再是能力證明

以前產出能當能力證明，是因為它難。現在一個人可以 vibe coding 弄出一個能跑的 app——但你問他用戶量上來會怎樣，他不知道；問他 AI 當初為什麼選這個架構，他聳肩；叫他不靠 AI 自己改一段，他改不動。

> **整個產業正在用史上最快的速度產出，用史上最低的程度理解。**

**對 junior 特別殘忍**：以前 junior 變強靠的是好幾年的瑣事——整理會議記錄、補文件、寫測試、清資料。沒人喜歡做，但**做的過程本身就是教育**：在一千件小事裡被有判斷力的人盯著，慢慢長出自己的判斷力。現在公司把這些瑣事自動化，順手也把靠這些瑣事在學的 junior 職缺砍掉了。「每一個今年被砍掉的 junior，都是一個本來會在三年後變成公司很需要的 senior，只是他不會出現了。」

反過來看，學徒制底下真正在運作的東西是**逼自己重複理解**，這個機制不需要一間公司，自己就建得起來：**量不重要，深度才重要。一個徹底搞懂的專案，比十個 vibe 完就丟掉的專案教你的多太多。**

**品味（taste）不是神秘美感**，是你把夠多東西理解得夠深，深到開始認得出哪些有效、哪些會壞、哪些重要。理解是長出品味的唯一路徑，而品味是每一波技術浪潮打過來都不會被沖走的東西。

### 但理解 ≠ 讀完每一行——關鍵是「對的介面」

管一個你不完全理解的東西，人類早就在幹了：CTO 不讀每一行 code，他看測試有沒有過；PM 不看後端怎麼實作，他直接拿產品來用；CEO 不對每一筆帳，他看那幾個關鍵數字。**共同點是都不靠讀完細節，而是靠一個對的介面去驗證真正重要的那幾件事。**

你跟 AI 的關係本質一模一樣。問題從來不是逼自己讀完 AI 吐的每個字，而是**有沒有一個夠好的介面，讓你用最低的力氣驗證到真正該驗證的東西**。

### 為什麼是 Markdown，又為什麼它開始不夠用

Markdown 之所以成為人與 agent 之間的通用語，是**因為它一直站在人這一端**：純文字、打得開改得動、可以 grep、可以用 git 看它改了哪幾行。講者舉證：Claude Code 與 OpenClaw 的記憶系統底層全是一堆 markdown 檔（一個 MEMORY.md 放長期記憶，每天的觀察寫成按日期命名的檔案）——**連 AI 自己的腦子，都選擇用對人類最透明的格式來存**。

不夠用的點不在 AI，**在人類看 markdown 的效率太低**。Anthropic 工程師 Thariq 在 X 上的文章〈**The Unreasonable Effectiveness of HTML**〉：現在超過一百行的 markdown 他自己就讀不下去了，更別說讓公司其他人讀。Markdown 放不了圖、沒辦法把兩個方案並排對比、沒辦法讓你動手調參數看看會怎樣。

> Markdown 是為了讓人好讀而生的格式，但 AI 越強、需要被人讀懂的東西越多越複雜，**markdown 反而最先撐不住**。

### HTML 的三個使用場景（重點是「不生成更多東西」）

1. **拿來比較**：不確定 onboarding 畫面怎麼做 → 叫 AI 一次生六個版本，版面／交互／資訊密度都不同，全排進同一頁，每個底下標清楚它做了什麼取捨，並排掃一眼就能比。Markdown 只能一個一個用文字描述，**你得在腦子裡自己把畫面拼回來——那個拼的動作就是審核成本**。
2. **拿來理解**：看不懂公司的 rate limiter → 叫 AI 讀完 code 產一頁 explainer，一張流程圖，底下留一區塊列有哪些坑，甚至出十題選擇題確認自己抓到重點。這就是**低耗能的審核**。
3. **拿來決策**：30 張 Jira 單要重排優先序 → 做一個網頁，每張 ticket 變成可拖的卡片，分成第一／第二／第三優先欄位；AI 先用它的判斷排好，你用拖拽調整，按一個按鈕**把整個結果轉成一段 prompt**貼回 Claude 繼續。

三個用法的共同點：**都不會生成更多東西塞給你看**，而是把複雜資訊變成一個能看、能比較、能下決定的介面。

**分工結論**：Markdown 適合承載**文字**；HTML 適合承載**狀態、關係、對比和互動**。要文字整理用 Markdown；要「回到一個任務、快速看懂狀態、比較方案、做決定」就用 HTML 工作頁。

講者自己的演化路徑很誠實：一開始掙扎要不要一行一行讀 AI 寫的 code → 後來只讀它生出來的 markdown → 再後來連那份 markdown 都掙扎要不要讀，因為太長了。**「我的注意力沒有跟著 AI 的產能一起變多。我需要的不是更多 output，而是更低成本的理解方式。」**

### 收尾：proof 要跟著 work 一起走

以前履歷／職稱／學歷／作品集有用，是因為做出一個像樣的東西本來就難。現在 AI 能生出有模有樣的作品，這些**越來越不能證明你真的懂**。真正稀缺的是能不能把理解跟作品綁在一起，能清楚回答四個問題：

1. 你做的東西是什麼？
2. 你為什麼選這個做法？
3. 這個東西在什麼情況下會壞掉？
4. 你在這次實作中學到了什麼？

三個「不要」：不要只追求更多產出，追求更深的理解；不要讓作品跟解釋分開，讓解釋本身變成產出的一部分；不要只靠履歷頭銜這些靜態標籤，而是用一個個**可驗證的完成紀錄**公開展示你怎麼判斷、怎麼取捨。

> HTML 並不是這部影片的重點，它只是 code → markdown → 可視化工作頁這條**資訊壓縮鏈**裡的一個階段。真正重要的是當 AI 把世界壓縮得越來越快，人還能不能留在 loop 裡繼續做判斷、承擔選擇，並且證明自己真的理解了。
>
> 你的價值不再是「我可以很快產出東西」，而是「**我能做出判斷，而且我能證明我理解自己交付了什麼**」。
