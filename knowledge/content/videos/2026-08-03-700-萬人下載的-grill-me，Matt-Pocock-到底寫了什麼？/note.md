**一句話總結**：Matt Pocock 開源了他馴服 AI 的整套 skill（16 萬星、700 萬下載），核心不是那個爆紅的 `/grill-me`，而是一個相反於大框架的主張——**skill 要小、要能拼裝、要用專業術語當壓縮指令**，而能寫出這種 skill 的前提是你本身是該領域專家。

## 為什麼他不做大框架

Matt 這一年重心全搬到 AI，發現比寫 code 更難的是**控制 AI 的隨機性**。市面上 Get Shit Done / Spec-Kit / Superpowers 都在解這題，但他認為大框架的病在於「想接管你整條開發流程」：Spec-Kit 把規格→計畫→實作綁成一條又重又硬的線，**前面一步定歪，錯誤會順著整條線傳染**，想改就得整條重跑。

所以他每個 skill 都刻意做得很小、很好改、能自由拼裝。

## 主幹流程

| Skill | 做什麼 | 背後的理由 |
|---|---|---|
| **grill-me** | AI 反過來拷問你，一次只問一題且附建議答案，沒共識前不准寫 code | 寫程式的本質是連續做幾百個微觀決定（防呆、斷線、極端資料）。Vibe Coding 等於把這幾百個決策權外包給黑盒子，而 AI 為了討好你會生出最難維護的架構。**這五行字的唯一目的是把決策權搶回人類手裡**——AI 負責挖盲點，拍板的永遠是人 |
| **to-spec** | 把共識寫成規格書 | **完全禁止 AI 在 spec 裡引用任何程式碼**。因為 code 比業務邏輯變得快，規格裡的過期 code 會讓下一次的 AI 越改越亂 |
| **to-tickets** | 規格拆成待辦 | AI 天生愛**按技術架構分工**（先建完資料庫→再寫完後端→最後畫前端），盲點是最後一步之前你什麼都測不了。to-tickets 強制改成**按使用者功能拆**：「會員登入」這一票就含它自己的 DB＋邏輯＋畫面，做完立刻能開瀏覽器驗。順便排序並標出可平行發包的任務 |
| **implement** | TDD 引導寫 code，寫完自動開**全新 session** 做 code review | **AI 骨子裡是作弊仔**：先寫功能再補測試的話，把「滿千折百」寫成折 200，它會生一個「滿千折 200，通過！」的假測試來交差。TDD 先把測試定死、亮紅燈，才准動手。開新 session review 是為了不被寫 code 時的記憶污染 |

Code review skill 不是空泛的「幫我看有沒有 bug」，而是把《Refactoring》裡 **12 種爛 code 症狀**寫成檢查清單。影片挑了三個：**Shotgun Surgery**（改一個按鈕顏色要開十幾個檔）、**Feature Envy**（訂單邏輯老是跑去庫存檔案拿資料）、**Data Clumps**（姓名/電話/地址永遠一起出現，就該打包成聯絡人）。

## 寫 skill 的三原則（藏在 `writing-great-skills` 裡）

這是全片最可移植的部分：

1. **修剪（pruning）**：多寫一句廢話，AI 就多一分分心。**連「你不說模型也知道」的指令都要刪掉**。這就是 grill-me 只有五行的原因。
2. **指引詞**：用**資訊被極度壓縮、含金量超高的專有名詞**。說一聲 `Data Clumps`，等於說完「請檢查有沒有總是綁在一起的變數，有的話打包成物件」。**一個字取代一百字的廢話**——前提是這個詞深植在模型的訓練資料裡。
3. **完成標準**：給 AI 一個明確的終點。

## 深模組 vs 淺模組

AI 寫得快但沒有大局觀，最愛蓋**淺模組**——像一棟房間分得很乾淨、卻沒有大門的房子，進廚房要爬窗、進客廳要爬煙囪。結帳被切成「算折扣／驗信用卡／建訂單／扣庫存／寄信」五個小房間，主程式得親自在五間房之間傳資料。

致命處在於**這種架構對 AI 無法維護**：context window 有限，修 bug 時它得在五個房間狂跳，塞不下就開始瞎猜，連原本正常的 code 都改壞。

**深模組**不是把一萬行塞同一間房，而是**蓋一扇極簡單的大門把複雜藏在裡面**（對外只有 `processCheckout`）。好處是「局部性」——出問題時 AI 只要讀這一個模組，來龍去脈全在視野裡。

`improve-codebase-architecture` 用**刪除測試**抓淺模組：想像把這個模組拔掉讓主程式自己處理會怎樣？拔掉後天下大亂 = 它真的有在隱藏複雜度；**拔掉後程式碼反而變清爽 = 它只是個多餘的空殼**。產出 HTML 診斷報告畫前後架構對比圖，當日常保養跑。

## 跟 Superpowers 的差別（作者的判斷）

- **Superpowers**：寫死的九個步驟，強制你想清楚目標、寫好文件才准動工。**在模型還笨、容易偏題的時代非常管用**，是「已經組好的自動化生產線」。缺點是產出的文件都為它自己的下一步量身打造，別人難接手。
- **Matt**：一個 skill 只解決一個問題，做完就收工。**手上已經有規格（自己寫的、主管給的、別的 AI 產的都行），可以直接跳到 to-tickets**，從哪步開始、哪步結束由你決定。

作者的結論：模型笨的時候需要保母級防呆；到了 GPT-5.6 Sol / Fable 5 這種等級，九個繁瑣步驟反而變累贅，**樂高積木比生產線更適合現在的生態**。

## 影片沒細講但點名的

- **grill-with-docs**（Matt 自己更常用的版本）：grill-me 的罩門是每次開工都要重新摸一次專案，前半場都在問背景，尖銳問題要等它摸熟才出得來。這個版本會在拷問過程順手把專有名詞和重要決策寫成文件留下，下次一開場就能切進重點。
- Matt repo 裡還有**三個 AI 寫作 skill**，作者說「比他寫程式的 skill 更值錢」、「顛覆我對 AI 寫作的認知」，但細節放在 Patreon 沒在影片講。

## 收尾論點

Matt 靠的是深厚的軟體工程底子，用在兩個地方：**架構上**（把深模組、爛 code 徵兆這些幾十年驗證過的老方法寫進 skill 來規範 AI）、**溝通上**（把專業術語直接當 prompt 的一部分）。

打破的迷思：很多人以為有了 AI 就不需要在自己領域精進。**恰恰相反——只有成為領域專家，你才控制得好 AI。**
