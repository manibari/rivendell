Harvard Business Review 今年二月發表了一篇研究
研究員花了八個月追蹤一家兩百人的美國科技公司
做了四十多場訪談
看看這些人在工作中導入了 AI 之後有什麼改變
結果令人意外的是， AI 不僅沒有幫你省事
反而讓人類更累了
工作量變多，步調變快
連原本不算工作時間的空檔，也開始被塞進各種事情
這一波生產力爆衝
最後換來的是壓力不斷堆積，認知疲勞，品質下滑，決策變差
到最後是 burnout 跟離職
看完這篇研究後
我腦中第一個想到的就是前陣子讀的一本書叫做 Four Thousand Weeks
裡面有個比喻我一直忘不掉，叫做現代版薛西弗斯
古希臘神話裡
薛西弗斯被懲罰要把一顆巨石推上山
結果石頭每次都會滾下來
他只能永遠重複同一件事
但在現代職場裡
薛西弗斯不是在推石頭，而是清理 email inbox
他剛剛把 inbox 清空
往椅背上一靠，深呼吸一口氣以為自己可以休息了
下一秒就聽到熟悉的提示音 你有新訊息
這本書的作者還有一句話講得很好
我們用來試圖掌控一切的科技，最後總是會失敗
因為它們會把那個『一切』本身變得更大
這就是 AI 帶來的真正問題
它不是單純幫你把工作做快一點
而是當你做事變快之後
組織很快就會把更多工作塞進來
你省下來的時間，不會自然變成休息
它更常變成下一個任務，下一封信，下一個會議，下一輪輸出
不過這份研究還揭露了一件更底層的事
AI 時代，你真正的瓶頸已經不是產出，是理解
以前你會做網頁，會寫 App ，會做報告，會做投影片
這些技能本身就能證明你的能力
因為做得出來就代表你會
現在 AI 把產出的成本壓到趨近於零
人人都能更快做出更多東西
於是能力的證明不再是你做不做得出來
而是你有沒有真的搞懂你做出來的東西
產出變便宜了，但理解變貴了
所以真正要解的問題不是怎麼逼 AI 多生一點東西出來
反而是怎麼樣能用最小的力氣就看懂並理解 AI 交回給你的東西
說到底這是一個格式問題
你跟 AI 之間用什麼形式在交接工作
直接決定你會不會被它的產出淹死
這支影片我會先拆解哈佛那份研究裡的生產力瓶頸
再講怎麼提高你審核 AI 產出的效率
最後談在這個時代，身為 AI Builder 或者 AI Developer
怎麼做才能真的脫穎而出
AI 讓工作變多，其實不難理解
農業時代靠人力
一個農夫一天能耕多少地就是極限
工業革命後能耕的地翻幾倍
但農夫要顧的機器，要規劃的範圍，要收的東西也跟著翻幾倍
AI 一模一樣，它讓產出變容易
大家的標準就跟著水漲船高
以前一週交一份報告就好，現在每天都要一份
哈佛那份研究把 AI 對上班族帶來的影響拆成三塊
我認為大多數人聽了都會深有同感
第一個是 task expansion ，工作範圍變大
產品經理開始寫 code ， marketing 開始做設計
不是公司正式改了職責
是 AI 讓這些事看起來變得可以嘗試
第二，工作跟非工作時間的邊界變模糊
以前是該上班就上班，該下班就下班
但現在你會順手寫個提示詞，反正只是一句話
反正它可以先跑，反正等一下回來看就好
第三， multitasking 變多
你一邊做自己的事，一邊讓它產文件
一邊等一個 agent 跑完
然後你又順手開了另一個 session
把拖了很久的事情也丟給它
確實每件事都在前進
但你的注意力其實一直在切換
實際上完成任務的效率是否真的有變高
相信各位一定比我還清楚
研究裡點出，真正讓人感到疲勞的
是不斷切換注意力，不斷檢查 AI 的產出
還有開著的任務越來越多
身為工作者，你需要不斷的檢查 AI 的產出
這就是在生產力上遇到的最大瓶頸
過去稀缺的是誰來做
現在稀缺的是誰來看，誰來判斷，誰來確認下一步
AI 可以把工作往前推
但每一個它推出來的東西
都要有人重新讀，重新理解，重新判斷
從而產生決策疲勞，腦子無法好好思考
如果只做一個專案那還好
因為可以一直待在同一個脈絡裡
可是 AI 的工作方式會自然而然的把你推向多工
因為它在跑的時候你不想乾等
你就會去開第二件事，第三件事
當你處理完第三件事再回到第一件事的時候
要重新閱讀，回憶剛剛發生什麼
你要知道哪些決定已經做過，哪些地方還沒過
哪些風險還沒有看
哪一段是 AI 自己亂補的，哪一段真的可以用
而且這種審核成本最麻煩的地方是
它不像加班時數那樣可以被量化
你沒有多開一場會，也沒有多交一份報表
可是你的腦子一直在切換，回想，比對，判斷
上級看不到這個成本，系統也不會記錄
最後就變成表面上工作更有效率，事情推進的更快了
但實際上自己累成狗
再往深一層想
產出這件事，以前能當能力的證明，是因為它很難
像是做一個 UI 介面，設計一套使用邏輯
要花力氣，花時間，也代表你真的會
現在一個人可以 vibe coding
一路寫提示詞，一路嘗試
弄出一個 app ，做一個小網站
但當你問他這東西當用戶量上來
或者遇到壓力測試時會怎樣，他不知道
你問他 AI 當初為什麼選這個架構，不選另外那個
他聳肩
你叫他不靠 AI 自己改一段，他改不動
他只知道這個產品會動
這個狀況同時在全世界很多公司發生
整個產業正在用史上最快的速度產出
用史上最低的程度理解
這對剛入行的人特別殘忍
以前一個 junior 變強靠的是好幾年的瑣事
整理會議記錄，補文件，寫測試，清資料
沒有人喜歡做這些，但做的過程本身就是教育
你在一千件小事裡，被已經有判斷力的人盯著
慢慢也長出自己的判斷力
現在公司把這些瑣事自動化
順手也把靠這些瑣事在學的 junior 職缺砍掉了
每一個今年被砍掉的 junior
都是一個本來會在三年後變成公司很需要的 senior
只是他不會出現了
但反過來看
學徒制底下那個真正在運作的東西，是逼自己重複理解
這個機制本身不需要一間公司，你自己就建得起來
方法就是逼自己搞懂每一個你產出的東西
量不重要，深度才重要
一個你徹底搞懂的專案
比十個 vibe 完就丟掉的專案，教你的東西多太多了
所以真正稀缺是你到底有沒有搞懂你做的東西
為什麼這樣設計，改了哪裡會垮
你刻意沒做什麼以及背後的原因
這種東西 AI 生不出來
你一旦不懂，多問兩句就會露餡
taste 也是從這裡長出來的
所謂品味不是什麼神秘的美感
是你把夠多東西理解得夠深
深到開始認得出哪些有效，哪些會壞，哪些重要
理解是長出品味的唯一路徑
而品味是每一波技術浪潮打過來都不會被沖走的東西
不過理解不等於你要把每一行都讀完
那從來就做不到，現在做不到
AI 出現之前也做不到
管一個你不完全理解的東西，人類早就在幹了
CTO 不會去讀每個工程師的每一行 code
他看的是測試有沒有過
PM 不會去看後端怎麼實作
他直接拿產品來用，看它有沒有解決問題
CEO 不會去對每一筆帳
他看的是那幾個關鍵數字對不對
他們的共同點是，都不是靠讀完細節
是靠一個對的介面
去驗證真正重要的那幾件事
你跟 AI 的關係，本質上一模一樣
所以問題從來不是逼自己讀完 AI 吐出來的每個字
是你有沒有一個夠好的介面
讓你用最低的力氣，驗證到真正該驗證的東西
那個夠好的介面，到底長什麼樣
這就回到格式
真正的槓桿不是逼 AI 多生一點
多生一點通常只是多一個你會丟掉的 AI slop
真正的槓桿是 AI 請你審核的時候
交付的東西是什麼格式
你跟 AI 之間
絕大多數時候是用 markdown 在溝通
markdown 會變成人跟 agent 之間的通用語
就是因為它對人夠友善
它是純文字，你打得開，改得動
你可以用 grep 搜索
可以用 git 指令看它到底改了哪幾行
舉個例子
現在最紅的兩個 agentic 系統
一個是 Claude Code ，一個是開源圈短時間衝上來的 OpenClaw
它們的記憶系統，底層全部是一堆 markdown 檔
一個 MEMORY markdown 放長期記憶
每天的觀察就寫成一個一個按日期命名的 markdown 檔
會這麼設計，是因為你隨時打得開
看得到這個 AI 到底記得什麼，不爽還可以直接改掉
連 AI 自己的腦子
都選擇用對人類最透明的格式來存
markdown 會贏，贏在它一直站在人這一端
但 agent 越來越強
markdown 反而開始不夠用了
講得更準確一點
不夠用的點在於人類看 markdown 的效率太低了
Anthropic 的工程師 Thariq 前陣子在 X 上寫了一篇文章分享這個轉變
文章的標題叫做 The Unreasonable Effectiveness of HTML
用白話文解釋這個標題的話就是 HTML 有效到離譜
他說現在超過一百行的 markdown
自己就讀不下去了
更不要說讓公司裡其他人讀
當 AI 寫的 spec 跟 plan
也就是規格文件跟實作計畫，越來越長，越來越複雜
markdown 那種好幾百行純文字的形式
理解的成本太高了
Markdown 沒辦法放一張圖
沒辦法把兩個方案擺在一起讓你並排對比
沒辦法讓你動手調一下參數看看會怎樣
分享給別人，別人也會看得很痛苦
換個方式講
markdown 是為了讓人好讀而生的格式
但 AI 越強
需要被人讀懂的東西越多越複雜
markdown 反而最先撐不住
那個工程師的解法，是改用 HTML 當輸出格式
HTML 用瀏覽器就能打開
能放圖，放表格，還能互動
這不是要你去學前端
是讓 AI 把它的產出直接做成這樣一頁你打開就能用的東西
接著我想分享三種使用場景
告訴你 HTML 是怎麼把原本很耗腦的理解跟判斷
變成一眼能懂，一看就能做決定的介面
第一個，拿來比較
你不確定一個 onboarding 畫面要怎麼呈現
你可以叫 AI 一次生六個版本
版面呈現，交互方式，資訊密度都不一樣
全部排進同一頁裡
每個底下標清楚它做了什麼取捨
讓你並排掃一眼就能比
這件事 markdown 做不到
它只能一個一個用文字描述
你得在腦子裡自己把畫面拼回來
那個拼的動作，就是審核成本
第二個，拿來理解
比方說你看不懂公司的 rate limiter 到底怎麼運作
你可以叫 AI 讀完相關的 code
產一頁 explainer ，一張流程圖
底下一個再特別留一個區塊告訴你有哪些坑是需要注意的
甚至可以出十題選擇題確認自己是否抓到重點
重點是讓你不用來回翻文件
也能知道重點在哪裡
一樣的資訊量
你可以更快的理解並做出決策
這就是低耗能的審核
第三個，拿來決策
假設你有三十張 Jira 單要重新排優先序
你可以叫 AI 做一個簡單的網頁
把每張 ticket 變成可以拖的卡片
分成第一優先，第二優先，第三優先等欄位
AI 會先用它的判斷幫你排好
你審核的方式不是去閱讀文字或者表格
而是打開網站
像是玩遊戲一下用拖拽的方式把這些工單分類
當你調整完畢之後，按一個按鈕
這個網站就會把整個結果轉成一段 prompt
你就可以貼回 Claude 讓它理解你的決策並繼續完成任務
這三個用法的共同點
是它們都不會生成更多東西塞給你看
而是把複雜資訊變成一個能看，能比較，能下決定
而且好理解的介面
但這裡我想先講清楚
我不會叫你用 HTML 全面取代 Markdown
也不是說哪個一定比較好
我自己一開始用 AI 寫 code 的時候
還會掙扎到底要不要一行一行讀它寫的 code
後來我開始只讀它生出來的 markdown 文件
再後來，連那份 markdown 文件，我都會掙扎到底要不要讀
因為真的太長了
我的注意力沒有跟著 AI 的產能一起變多
我需要的不是更多 output
而是更低成本的理解方式
這也是 Markdown 的能力邊界
也是 HTML 的價值所在
HTML 不是比較高級的 Markdown
而是另一種工作介面
Markdown 比較適合承載文字
HTML 比較適合承載狀態，關係，對比和互動
所以如果你要在兩者之間做決策
真正的問題是你想解決什麼問題
如果你要的是文字整理，用 Markdown
如果你要的是回到一個任務，快速看懂狀態，比較方案，做決定
那 HTML 工作頁或許更適合
不過我不希望這支影片只停留在工具層面
我想順著聊聊你身為 AI Builder 或者 AI Developer
在這個時代下應該要怎麼做才能脫穎而出
Markdown 也好， HTML 也好
真正重要的點在於你有沒有理解 AI 這個黑盒子裡面到底發生了什麼事？
你身為一個 builder
真的知道自己在做什麼嗎？
或者你只是在 Claude 跟你請求許可時一直按 Enter
根本不知道自己批准了什麼
AI 時代最大的變化是，產出變得太便宜了
以前履歷，職稱，學歷，作品集有用
是因為做出一個像樣的東西本來就很難
你做得出來，某種程度上就代表你會
但現在不是這樣了
AI 可以幫你生出一個有模有樣的作品
一份很漂亮的報告，或者一個能跑的 prototype
但這些東西本身
已經越來越不能證明你真的懂
真正稀缺的是你能不能把理解跟作品綁在一起
不是只交出一個結果
而是能不能清楚的回答這四個問題
你做的東西是什麼？
你為什麼選擇這個做法？
這個東西在什麼情況下會壞掉？
你在這次的實作中學到了什麼？
AI 時代的能力證明
不要只追求更多產出，而是追求更深的理解
不要讓作品跟解釋分開
而是讓解釋本身變成產出的一部分
不要只靠履歷，頭銜， credentials 這些靜態標籤
而是用一個個可驗證的完成紀錄
公開展示你怎麼判斷，怎麼取捨
怎麼理解自己交付的東西
這就是我認為接下來很重要的一件事
proof 要跟著 work 一起走
你的能力證明不能止步於履歷
它要留在你的作品裡
我最近在整理自己做過的專案
寫了幾個提示詞可以用引導式的方法幫你回答剛剛提到的核心四問
完整的提示詞我放在 Patreon 的文章裡面
有興趣的朋友可以在影片下方資訊欄找到連結
HTML 並不是這部影片的重點
它只是 code 到 markdown
再到可視化工作頁這條資訊壓縮鏈裡的一個階段
真正重要的是當 AI 把世界壓縮得越來越快
人還能不能留在 loop 裡
繼續做判斷，承擔選擇，並且證明自己真的理解了
你的價值不再是我可以很快產出東西
你的價值是 我能做出判斷
而且我能證明我理解自己交付了什麼
這是我認為接下來最值得押注的事
