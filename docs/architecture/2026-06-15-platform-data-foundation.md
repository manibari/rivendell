# Design: Rivendell Platform Data Foundation + Version/Roadmap Feature

## Problem Statement

Rivendell today is a skills library + automation platform with a **read-only**
dashboard (`api/` Python service over filesystem-derived data + Next 16 frontend).
The user wants it to grow into an **active control plane**: automated deployment
(+ GitHub update/pull→build→deploy→report), Cloudflare domain/Tunnel management,
and Docker container oversight. First concrete feature: a **version-management +
roadmap** panel (modeled on ChimesFlow).

## Demand / Status Quo (from diagnostic)

- **Deploy**: manual ssh/scripts, steps forgotten, env drift. Biggest pain. Wants
  rivendell to automate deploy + GitHub updates.
- **Domains/Cloudflare**: scattered in the CF web console; no single view of which
  domain/Tunnel maps to which service.
- **Docker**: container state opaque — `docker ps` one host at a time, no overview.

These are real, recurring, self-inflicted-toil pains — not hypothetical.

## Target wedge & sequencing

First feature (narrowest wedge, chosen from strength): **version/roadmap panel**
— single-writer, small data, low risk, aligns with the just-created ROADMAP.md /
CHANGELOG.md. The painful control-plane features (deploy → docker → domain →
github) follow once the foundation is proven.

## Premises (agreed via diagnostic)

1. Rivendell moves from read-only dashboard → control plane that **executes**
   actions (deploy/docker/domain/github). ✅
2. Version/roadmap is the first table; small + single-writer **now**. ✅
3. Future write profile is **concurrent multi-writer** (deploy workers, agents,
   dashboard all writing deploy/container/sync state). ✅

## Decision: data foundation = PostgreSQL now (Docker)

**User chose Postgres-now over the SQLite-now-PG-ready recommendation.** Rationale
(user-owned, defensible): docker management is already on the roadmap, so a `pg`
container is low marginal ops cost; the concurrent multi-writer future is real;
prefer paying the foundation cost once over migrating later.

- **Engine**: PostgreSQL in a Docker container (local, on the personal machine;
  exposed via existing launchd + Cloudflare Tunnel pattern, NOT public).
- **Access layer**: SQLAlchemy + Alembic in the existing Python `api/` service
  (same stack as ChimesFlow → near-direct port, not a rewrite).
- **First schema**: port ChimesFlow's `release_items` table (see below).
- **Security/right-size note**: this is heavier than the row-count justifies today
  (per CLAUDE.md Right-size infra). Accepted as a deliberate one-time foundation
  bet for the concurrent-writer control plane. Revisit if the control-plane
  features stall — an idle Postgres container is pure ops overhead.

## Feature design: version/roadmap (ported from ChimesFlow)

ChimesFlow unifies version + roadmap in ONE table; status filters pick the view
(shipped → changelog, all → roadmap). Port that design.

**Schema `release_items`** (Postgres; JSONB for visibility):
`id` UUID · `version` text? · `title` text · `description` text? (markdown) ·
`status` (planned|in_progress|shipped|archived) · `target_date` date? ·
`shipped_at` timestamptz? (auto-stamped on →shipped) · `module` text? (swim-lane) ·
`sort_order` int · `parent_id` self-FK? · `created_at`/`updated_at`.
(Drop ChimesFlow's `source_feedback_id`/RBAC `visible_to_roles` for v1 — solo, no
feedback system yet. Keep columns nullable so they can return later.)

**API** (Python `api/`): `GET /api/roadmap` (all), `GET /api/roadmap/recent`
(shipped), `POST/PUT/DELETE /api/roadmap/{id}`.

**UI** (`src/app/roadmap/page.tsx`, Tailwind+lucide to match existing panels):
changelog timeline (shipped, SemVer-colored) + roadmap kanban/timeline (all
statuses, module swim-lanes). Version badge in sidebar footer (version + build SHA).

## SoT resolution (resolves the markdown-vs-DB tension)

DB becomes the **live SoT** for roadmap/changelog. The just-created
`ROADMAP.md`/`CHANGELOG.md` shift role: **generated exports from the DB** on each
release, committed for git-visible history. `doc-drift-sync`'s job narrows to
verifying the export matches the DB (no two hand-edited SoTs). Seed the DB from
the current ROADMAP.md/CHANGELOG.md contents.

## Approaches considered (data foundation)

- **A. SQLite-now, SQLAlchemy, PG-ready** (recommended by skill) — zero PG ops,
  migrate when concurrent features land. Rejected by user.
- **B. Postgres-now (Docker)** — **CHOSEN**. Pay foundation once; fits concurrent
  future + docker comfort.
- **C. Markdown SoT only** — insufficient for a concurrent-writer control plane.

## Open questions — RESOLVED by eng review (2026-06-15)

1. **Container lifecycle**: `docker-compose.yml` in repo (declarative, versioned) +
   launchd wrapper `com.sk.pg` runs `docker compose up -d` at boot; restart
   `unless-stopped`, named volume. NOT a hand-rolled `docker run` script.
   New SPOF: Docker Desktop must be running → `api/` must **degrade gracefully**
   (roadmap page shows "DB unavailable", not a 500).
2. **Backups**: launchd `sk-pg-backup-cron` nightly `pg_dump` → gzip → dir OUTSIDE
   the repo, 14-day retention. (The git-committed ROADMAP.md/CHANGELOG.md exports
   are a partial secondary backup — free from the SoT-export design.)
3. **Connection layer**: existing `api/server.py` takes the DB (no new service,
   YAGNI). SQLAlchemy engine + `pool_pre_ping=True`. Alembic migrations run as an
   explicit `sk db migrate` step, NOT per-worker (concurrent-migration race). DB URL
   in `~/.config/` (chmod 600, like the telegram token), never in the repo.
4. **SoT drift**: ROADMAP.md/CHANGELOG.md get an `AUTO-GENERATED FROM DB — don't
   hand-edit` header; `doc-drift-sync` flips to "verify export == DB, fail on
   hand-edit". One-time seed script parses current md → DB rows.
5. **Auth (P1)**: **Cloudflare Access gates the whole dashboard** at the Tunnel
   layer — only the owner's identity gets in. No app-layer auth code. (Without this,
   write endpoints over the Tunnel are world-writable.)
6. **Right-size checkpoint**: if no second DB-backed feature lands within ~2 months
   (one iteration cadence), revisit whether PG earns its keep vs the idle-container
   ops cost. Migration-back via SQLAlchemy is possible but unlikely in practice.
7. Build SHA/date injection into Next 16 (next.config.ts git env, like ChimesFlow).

## Test strategy

Test against PG (not SQLite — dialect drift), disposable test container + per-test
transaction rollback. Cover behavior, not just CRUD: status→shipped auto-stamps
`shipped_at`; roadmap-vs-changelog status filtering; **export == DB**; md-seed.

## VERDICT: GO (with P1 auth as a ship-blocker)

Architecture is sound for the chosen Postgres-now bet. One P1 (auth) resolved
(Cloudflare Access). Right-size tension acknowledged with a 2-month checkpoint.
Cleared to implement, starting with the assignment (stand up PG + `SELECT 1`).

## Success criteria

- `release_items` in Postgres; `/api/roadmap` serves it; `/roadmap` page renders
  changelog + roadmap views; version badge shows current version + build SHA.
- ROADMAP.md/CHANGELOG.md generated from DB, matching, committed.

## Distribution

Internal — runs on the personal machine via launchd + Cloudflare Tunnel. No app
store / package. The PG container is the only new infra to stand up.
