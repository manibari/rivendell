這張圖要 argue 的事

靜默失敗只發生在沒有登記處的帶。 今晚三個 root cause 全部落在紅色與黃色帶上，沒有一個落在綠色帶：

今晚的失敗發生在哪一帶為什麼那裡會出事
R1 兩個 .db 檔分裂（資料落點，同樣無登記處）寫入端與讀取端各自寫死檔名，沒有一張表說「這個表住哪」
R2 registry 產生器失敗被吞工具帶相依的 PyYAML 不在任何宣告裡，錯誤回退到不存在的快取
R3 服務跑一個月舊建置工作流帶沒有任何機制知道「建置」和「服務」之間該有什麼保證

反過來說也成立：skills 和 agents 那兩帶今晚一個問題都沒有出， 而它們是唯二有 schema 的。registry v2 上個月才落地，`sk check agents` 就已經能抓到排程漂移。

所以「重新整理架構」的具體動作不是搬檔案，是把 registry v2 這個模式複製到另外四帶。

跟外面的東西比

最接近的公開架構是 Dify：Model Providers / Tools(Plugins) / Knowledge Base / Workflow / Node System。 每個域都是 DB 支撐 + manifest schema。rivendell 是同一個形狀的檔案原生版本—— agents/registry/*.md 加 schema_version 就是 Dify plugin manifest 的 git 版。

概念Difyrivendell 現況
模型Model Providers，workspace 層憑證管理寫死在 4 支腳本
工具Plugin 六型 + manifest schemaallowed-tools 39/125 + $HOME 的 hooks
知識庫向量庫 + PG metadata，一個 RAG pipeline四個落點，無索引
工作流版本化、PG 支撐、可回滾三套機制，只有一套有狀態
提示詞沒有獨立登記處，住在 node config 裡SKILL.md 本身即提示詞
skills沒有這個概念125 支，有 schema，可對帳

兩件事值得注意：提示詞不該獨立成一軸（Dify 把它放進節點，rivendell 放進 SKILL.md，兩邊結論一樣）； skills 是 rivendell 有而 Dify 沒有的——那是差異化，不是缺口。

所以要補的其實是 三 帶，不是四帶：模型、工具、知識庫。

依 2026-09-18 實查：模型字串出自 grep -rnoE over bin/； 工具數字出自 ~/.claude/settings.json 與 125 份 SKILL.md； 知識庫檔數為當日 find 實測；agents 為 agents/registry/ 實數。
